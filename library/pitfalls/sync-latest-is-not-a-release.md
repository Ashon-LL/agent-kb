**经验**：用户说「同步 / 更新 / 都要最新 / 落实」时，动作上限 = **把目标载体对齐到同一最新状态**（本地检出、远端分支、安装区、消费方各端），**做到即停**。⛔ 不得升格为「bump 版本号 → 重新构建 → 出安装包 → 打 tag → 合并发布线」的发布动作链——发布链只有用户**明说**「发版 / 出包 / bump / 打 tag」才启动。

**Why**：对齐是幂等的读/拷动作，发布是改变产品语义的写动作——它动版本号、跑几十分钟构建、产生不可静默撤销的 tag 与发布记录。把「要最新」擅自执行成发版：① 多出的版本号/tag 污染发布线（用户没要）；② 构建产物出错还得回滚，成本远超收益；③ 用户当场叫停（实锤 2026-10-06：「我没有说打 tag，为什么要重新构建」「不要自作主张」）。同族升格还有：把「更新」扩成「升级依赖」、把「同步」扩成「重建索引」——**判据：用户措辞的动作等级 = 动作上限，不得升格**（与 [[prohibitions-need-second-confirmation]] 的「措辞不得比原文宽」互为两面：一个是加禁止、一个是升动作）。

**How to apply**：收到「同步/更新/最新」类指令，先映射为**最小动作集**（如 git push/pull + merge 对齐 + 安装区官方同步脚本），逐项做完后逐端对账（逐文件 hash / 逐端 rev-parse）并汇报对齐证据即收尾。准备升格动作（发版/发布/重建/打 tag）前，**必须**先拿到包含该动作词的明确指令；拿不准就只做对齐、把升格项列出来等一句确认，而不是先做一半。
