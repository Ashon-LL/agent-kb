**经验**：用户用「A=B > C > D=E=F > G」这种写法给你排序时，`=` 是他**明确的并列意图**，`>` 才是先后。
落值必须让每个 `=` 组变成**完全相同的数值**，而且**展示时同档成员只能用并列符号**（`‖` / "并列"），
`>` 与 `→` **只允许出现在跨档**。把同档内的差别（哪怕是真实的抽签比例差别）写成先后关系，
用户读到的就是"你把并列改成了先后"，会直接判定你没看懂他的输入。

**Why**：APIShow「临期优先」组的 priority/weight 设计里，用户给的顺序是
`Loomy=Raccoon > 商汤 > WorkBuddy > CodeArts=Trae=LobsterAI > Astron`。
我把各组落成了 10/9/8/7/6（等号关系其实保住了），但在**尝试链展示**里为了表达"同档按权重抽签谁占优"，
写成了 `Loomy ＞ Raccoon`、`Trae ＞ CodeArts ＞ LobsterAI` —— 用户当场质问
「你没看优先级中我说的有相等的部分吗？权重中我说的也有相等的部分」。
同一轮他还补了两条口径：**不希望出现 0 值**（最低档也要给正数）、以及「小心谨慎」（生产写操作要分步验证）。

**How to apply**：
1. **落值**：先把他给的字符串拆成档位，再一档一个数（档间差 1 即可，别自作主张留奇怪空档）；
   他点名的对象之外若还有别的对象（本例：Qoder / OpenCode / CNB 三个不在榜单里的渠道），
   **照给数值但明说"这是我给的、不在你的榜单里"**，留一个否决口。
2. **自检表**：交付时附一张「你的排序 → 我的数值」对照表，等号组并排写 `10 = 10`，让他一眼验完。
3. **符号纪律**：同档用 `‖`；`→` 只用于跨档；同档内谁分到多少用**比例**说明（"同档按权重抽签 8 : 6"），
   不要写成先后。
4. **生产写**：他说"小心谨慎"就拆成先加后删两步，每步做真请求 e2e + 回读断言 + 备份，
   并在汇报里显式声明**哪些部分没动**（本例：未动 options）。
