**事故**：给 ZCode 的 agent 进程加「15 分钟空闲回收清扫器」。装机一天，回收 0 次，进程从 9 涨到 23、
内存 2.1→5.2GB。用户：「为什么没能做到回收？我要求要做到回收。」

**Why**（两个都是我自己的实现错误，不是环境问题）：

1. **安装点挂错了**：清扫器只在 `scheduleIdleReclaim()` 开头调用安装。而这个函数本身在 3.16.2 的
   这批工作区上**一整天 0 次调用**（应用自带的空闲回收日志也是 0 条）。结果：清扫器从未安装。
   把修复挂在"另一个可能同样失效的机制"上，等于没有修复。
2. **观测写错了地方**：用 `console.log` 记回收事件。打包版 Electron 的 host/main 进程 console
   **没有落盘通道**，日志等于不存在，所以"没跑"和"跑了没记录"无法区分。

**How to apply**：
1. 安装点选在**你这个目标必然发生的事件**上（这里是 agent spawn：当天实测 21 次），
   不要选在"上游本应调用"的钩子上；入口函数处的安装可以保留做双保险，但不能是唯一路径。
2. 诊断类代码**自己写文件**（带时间戳），不要依赖 app 的日志通道；每 N 次 tick 记一次上下文
   （输入值 + 决策 + 原因），否则失败后仍只能猜。
3. 判断"改生效了吗"要用**独立于改动的证据**：进程数/内存曲线/回收日志，而不是代码在不在包里。
4. 先证明机制被触发（安装行），再谈效果（RECLAIM 行）；两件事分开验证。
