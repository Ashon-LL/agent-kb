**经验**：日志/报表里看到「N 条相同（或高度相似）错误」时，先别按 N 次故障叙述，先跑**同源四验**：

1. **锚点 ID 是否同一个** —— sessionId / runId / 容器 ID / 构建号 / trace-id；同一个往往意味「一次运行被归因给 N 个对象」。
2. **耗时是否 = 总时长 ÷ N** —— batch 型归因常把一次运行的总时长**均摊**给每个对象（本例 813s ÷ 23 ≈ 35s，23 条逐字相同）。
3. **时间戳是否同一瞬间齐发** —— 批量落盘（毫秒级连发）= 事后归因；顺序错开数分钟才是独立发生。
4. **错误原文是否逐字全同** —— 真独立故障几乎不会连上下文相关片段都字字一致。

四验指向同源 ⇒ 叙述写成「**1 次事件（原因 X），影响 N 个对象**」，并分开给两个数：**独立事件数**与**受影响对象数**（本例：事件 1 起；对象 23 张；整批口径的 done=27 / 成功 2 / 失败 25 另行列出）。

**Why**：2026-10-08 实弹——续跑的炼制会话上下文溢出（估算 236K > 预算 217.5K）→ 自动压缩成功 → 压缩后重试那一次上游返回 `incomplete or malformed tool call` → 会话级失败（1 次）→ 批次把这一次失败**逐字**归因给 23 张待炼工单（同一 sessionId、同一 reason、elapsed 全为 813s/23）。若读成「23 张各自失败」，会把一次上游瞬时故障误报成 23 个独立缺陷，复盘与派单全都会歪，还会错配修法（该修防重试，却去逐张查工单）。
同族前科：把「一条 warn 的一瞬」当终态 ⇒ 误判整批 0 产出。

**How to apply**：
- 汇报 / 派单 / 复盘前跑四验；同源先降维成「1 次事件」再找根因，影响面另述。
- 归因链里显式写清「事件数 vs 对象数」，且**别拿均摊耗时当单对象耗时**（35s 不是每张的真实用时）。
- 与 [[log-full-read-not-just-errors]] 互补——那条讲读全量（别只筛 error），本条讲读出的条数**先去重同源**；
  与 [[log-text-is-not-spec-read-emitting-code]] 互补——那条讲别信文案字面，本条讲别信条数。
