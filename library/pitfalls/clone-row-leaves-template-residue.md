**经验**：用「克隆一条现有记录 + 改几个字段」来新建配置，快但危险——**你只覆盖了你想得到的字段，其余全部静默继承模板的值**。残留分两类：

- **有功能影响的**：本次 `channel_info` 里 `multi_key_size=3` 跟着模板带过来，但新渠道只放了 1 把密钥 → 重试逻辑会去取不存在的第 2、3 把钥。
- **纯元数据/统计的**（更隐蔽）：`remark`（凭据标签）、`used_quota`（用量）、`test_time`/`response_time`（"已测试"时间）、`settings` 里模板上游的模型清单。它们不影响运行，但**界面会原样显示给用户**——本次用户就是看到渠道卡片上写着「**商汤API密钥**」「**已启用 (3/3)**」「**+8**」才发现我占了商汤的东西。

**Why**：2026-09-19 建 New API 渠道 ch176（WorkBuddy）时，我克隆了 ch29（商汤）整行作模板，只覆盖了 name/base_url/key/models/mapping/group/status/priority/weight 等，**7 个字段带进商汤残留**。用户从 UI 上发现并质问「你怎么占有了商汤的东西」。同时我还犯了两个相关错误：① 凭感觉造了一个**不存在的枚举值**（`kind="upstream_gateway"`，而本仓只有 `account_pool`/`adapter`/`openai_compat`/`official_api` 四种）；② **顺手翻转了邻接字段**——把两个 legacy 模型的 `sellable` 从 `false` 改成 `true`，用户只要求接入新模型、没要求上架旧模型。用户的批评原话：「**应该对应的去更改，而不是无脑复用**」。

**How to apply**：

1. **首选逐字段显式构造**，不要 clone+patch：把目标记录的完整字段清单列出来，**每个都赋值**（哪怕是空值/零值）。字段多到不现实时才考虑克隆。
2. **若必须克隆，事后做全字段 diff**：把模板记录与新记录逐字段对比，**凡"值相同"的字段都要问一句"这个值本该相同吗？"**——相同的越多越可疑。
3. **检测残留的可靠判据是「值重复」而非语义启发式**：跨记录**完全相同**的 `used_quota` / `test_time` / `created_time` / `remark` 就是克隆指纹，噪声极低。（我第一版判据写成"settings 里的探测模型与本记录模型零重叠"，**全是假阳性**——那个字段本来就是上游**其他**模型的清单，ch29 探测出 sensenova 系列恰恰是正确行为。换用「值重复」后一次就定位准了。）
4. **枚举/命名类字段先查既有取值分布再赋值**，不要凭感觉造新值。一行 `Counter(现有取值)` 就能看到合法集合与惯例（如 `remark` 是「<厂商>API密钥」格式、`kind` 只有 4 种）。
5. **只改被要求的字段**——不要顺手改邻接字段。想改就先问，或明确列为"建议"而不是直接做。
6. **交付前把「我改了什么」逐条列成表**（字段名 + 旧值 → 新值 + 理由），用户才能一眼看出有没有夹带范围外改动。
7. 修残留时**逐字段 UPDATE**，不要整行覆盖（整行覆盖会把期间被系统改过的字段——如自动探测时间——一并回退）。
