**经验**：给常驻进程/会话加「空闲回收」时，**判据的第一选择必须是「有没有事在做」，而不是「有没有人在看」**。任何基于 UI 状态的判据（有没有订阅、有没有打开的标签、有没有前台窗口）都隐含假设了「所有工作都来自人的操作」——而定时任务、无人值守、自动化流水线恰恰是「UI 不在场但活照样在干」。这种场景下 UI 状态判据**不是不准，而是结构上失效**：改选择器、改轮询间隔、加日志都救不了它。

**Why**：真案例——ZCode 桌面端给「工作区 agent 进程」加了 15 分钟空闲回收，判据是「该工作区还有没有 UI 的会话订阅」。上线当天 03:45 就把用户一个 03:30 启动的**无人值守自动化任务**（面板全程关闭）的进程回收了，任务中断。定位时拿到决定性证据：该任务运行的 15 分钟里，UI 侧会话订阅事件数 = **0**（对照正常时段 01:51/01:54/02:03 都有完整的 `started → acknowledged → activated` 三连）。原因是那个 agent 由「只读会话控制面」启动，UI 从来不订阅它。而同期日志里明明有稳定的活动信号——每分钟一次 `queryConversationCommandsV4 OK (51.6ms)`——一直被当成噪音忽略了。换成「最近收到过 CLI 通知」（CLI 一干活就推消息增量/工具调用/状态变化）后，UI 在看、无人值守、自动化任务三种场景一视同仁全覆盖。

**How to apply**：
1. **先枚举场景再定判据**：写下这个进程所有可能的「活着」形态（人在用 / 定时任务 / CI 流水线 / 后台同步 / 被别的服务调用），再检查候选判据对**每一种**是否都能观测到。只要有一种观测不到，就换判据，不要指望调阈值弥补。
2. **优先用「对端主动推的东西」当判据**：心跳、通知、事件流——它是双方共有的信号，与谁在场无关。比「查 CPU/内存/句柄数」更稳（那些要采样、要权限、要处理抖动），比「问它你还在吗」便宜（不用改协议）。
3. **挂点选在记录构造处**：`onNotification(() => lastActiveAt.set(key, Date.now()))`，try/catch 包住（监听失败不能拖垮主流程）；判据函数读 Map + 一个宽限窗口（默认 2 分钟，宁可误判忙也不要误杀）。
4. **阈值和判据是两件事，别混着改**：修误杀应该改判据；顺手把默认阈值从 15 分钟拉到 60 分钟是**未经授权改用户配置**，会被明确要求撤回。正确做法是判据修好后阈值原样不动。
5. **复盘要拿「事件计数」当证据**：不要只说「日志里没看到订阅」，要数出来——「该时段订阅事件 0 条，对照时段 3 条/次」，这样才排除「我 grep 漏了」。
