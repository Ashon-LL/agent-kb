# 「同步到最新」要打到用户拿到东西的那一层——本地副本不算数

**现象**（2026-10-20，用户两次追问「尽快」「继续啊 怎么回事」之后才定位）：
用户要求「把本地所有更新到最新……我打开软件时要看到修复后的，不是只更新开发区」。
我在本地重建容器镜像两轮（`docker commit` 与 `docker build` 都试过），容器内文件校验也对上了，
但用户的启动器第 [2/4] 步是**无条件**
`docker pull <制品库>:0.9.11` + `docker tag` 覆盖本地同名镜像
⇒ 我改的本地镜像**每次启动都被远端旧镜像盖回去**。真正的修复点是**推制品库**。

**问题出在哪**：
- 我只验证了「**我这一侧**的产物是对的」，没验证「**用户那一侧拿到的东西**」中间经过哪些环节。
  有一层（启动器）会主动用远端覆盖本地，这一层不看就等于没改；
- 更隐蔽的是**第二条断点**：`frontend/dist` 是 gitignored 的常驻目录，而所有
  「读产物」的用例在 dist 存在时**直接读、不重建** ⇒ 工作区里一份旧 dist 把
  「源码能不能编译」这件事藏了一整天（真实后果：HEAD 前端当时**编译不过**，
  而全量套件看起来是"绿"的）。

**怎么防（三条）**：
1. **先画交付链，再动手**：用户 → 启动器/安装器 → 制品库/分发渠道 → 本地副本。
   先问一句「**我改的这一层，是不是用户拿到的那一层**」；不是就往上游打到那一层为止。
2. **验证必须在用户路径上做**：不要只 `docker exec` 看文件在不在，要
   **从制品库回拉**（digest 比对）+ 走**用户会走的入口**（HTTP 端点、页面）实测一次。
3. **旧产物一律按"可能过期"处理**：gitignored 的构建产物、缓存、上次生成的 dist——
   凡被下游用例/服务直接消费的，要么补新鲜度判据，要么每次都重建。
