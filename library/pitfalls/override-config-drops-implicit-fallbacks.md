给外部工具传**覆盖式配置**（`--config <file>` / `--isolated` / 自己生成一份最小配置）时，
工具会**只认这一份文件**，交互式安装/向导替用户填好的隐式默认**全部丢失**。
⇒ 凡是程序化路径依赖的能力，都必须**自己显式声明**；漏一个的后果是**静默降级**
（工具不报错、判据恒不成立、功能形同关闭），而不是失败。

**症状**：同一工具「正常手动用没事，自动化一跑就出问题」。人手动用时向导/onboarding 已经
把该配的都配了；headless 路径没人做这一步。

## 三个必须记住的坑（同族，实测）

### ① 声明的字段可能只是「可见性」，不等于「可用性」
配置里声明了某能力档位（profile / allow），只让工具**出现在工具清单里**；
它的**执行后端**可能是另一套独立配置面，需要**单独显式选中**。
例：`web_search` 是自带工具（已在 profile 里），但它执行时要选一个搜索后端；
官方文档明写「免密钥后端 **never win auto-detection**，只能显式选中」。
⇒ 判断方法：**别读配置字段名，去读消费它的代码/官方 doc**，看它到底认什么。

### ② 声明一个**不可用**的值会让**整份配置失效**（fail-closed）
实测：声明一个未安装的扩展/不存在的路径 ⇒ 校验直接 `invalid`，工具**拒绝运行**，
而不是"忽略这一项继续跑"。
⇒ 因此这类开关**不能硬编码**，只能做成「运维输入」，且**默认留空**（= 不声明 = 保持历史行为）。

### ③ 顺序纪律：全局注入型开关必须「先就绪、后声明」
若配置文件是**全局注入**的（所有任务共用），一旦它 invalid，**所有任务一起挂**。
⇒ 正确顺序 = ① 先把依赖（扩展/插件/路径）在目标环境**真实装好** →
② 用探针验证「该值在本环境可用」→ ③ **才**打开声明开关。
反例顺序（先开开关后装东西）会把整个流水线打死。

## 扩展的可见性还常随「工作目录 / state 目录」解析
非内置扩展往往只从「当前 state-dir / 工作目录 / 全局根」里找。
若每个任务用**独立的 state-dir**（隔离），在别处装的扩展对具体任务**不可见**。
⇒ 找官方支持的「额外加载路径」配置项（如 `plugins.load.paths`），指向一个
**确定性路径**的共享目录。

⛔ **别用带随机 hash 的缓存路径**做这个共享目录。工具自己的 `install` 子命令常落到
`<cache>/<pkg>-<hash>/…`，**每次不同、无法硬编码**；改用包管理器的
`--prefix <固定目录>` 之类搞出确定路径。

## 通用排查手法
1. 先问工具**自己**：「有哪些可用后端/扩展？」（`<tool> <cap> providers --list` 这类命令）
   —— 比读源码猜快得多，且是经验证据。
2. **双向对照实验**：带上声明 / 去掉声明各跑一次，看差异 —— 证明「有效性来自哪一项」。
3. 官方自带 `docs/` 常随包分发，直接 `grep` 它的文档比搜网快且准确。
