**经验**：引用配置值区分"程序默认值"与"谁设的"，说清作用域。推断前核对量纲（累计量≠瞬时量）。统计前确定口径（成功 vs 全部、哪个状态码、哪个时间窗）。被追问出处而自己查实是错的，明确收回推论并说明错在哪。

**Why**：拿 24h 累计调用 539 次去比 max_in_flight:3（瞬时在途上限）说"这个号会先触顶"——量纲不同不可比。拿 max_in_flight_global:2 去套 CN 号——CN 号走的是 max_in_flight:3 那一档。统计签到只 grep "签到成功" 看到 4 行就报 4 个号成功，漏了另外 4 个"今天已签到（幂等）"。更深层：把"配置里没有这个键"翻译成"功能没开"——判据应该是运行证据（台账 kind、日志、enabled 标志），不是配置文件字段有无。

**How to apply**：判"某任务在不在跑"先取运行侧证据。报"不存在/没跑"前先问"我用的是存在性判据还是仅仅是没搜到"。记忆里已有定谳的事实执行前先回读，不要凭印象重推。用户拿 UI 证据反问时先问"我们说的是同一件事吗"而不是先假设"我错了"。


## 2026-11-10 补：minified 中文 UI 里「英文组件名 0 命中」≠「功能不存在」（zcodepro 调研 v1 事故）

**同一事实的新反例，扩充本条**：在二次改造的闭源 Electron 成品包（果冻注入的中文 UI）里做
「有没有某功能」的盘点，我用 `usedPercentage` / `ContextWindowProgress` / `totalCost` /
`Most Expensive` 这些**上游开源项目的英文组件名**在 `out/styles` 里计数，全是 0 就写进报告：
「上下文占用可视化、费用排序、历史检索都是真缺口」。

用户用两张实机截图直接否证：**上下文容量**（45.2万/96万 47.1% 进度条 + 消息/系统工具/MCP 工具等
六类占比 + 平均缓存命中率 + 压缩按钮）与**重试与错误**（本轮/今日重试、按错误码、最近 60 条明细）
不但存在，还比竞品更细。改用中文文案重扫，`上下文容量`/`重试与错误`/`今日重试`/`按错误码`/
`恢复会话`/`归档管理`/`快捷键`/`定时` 全部命中。注意 `contextWindow` 命中 52 次却**全是
framer-motion 的 DOM window 变量**，与上下文窗口无关——命中数也会骗人。

**根因**：minified 产物里组件名被压缩/替换，注入层用的是中文字符串；搜索词选错「层」，
0 命中只证明「这个字符串不在」，连「没搜到」都不是，更不是「功能没有」。同类地，
`/rewind` 命中 2 处其实是 vite 图标文件名 `rewind-CrplcSpC.js`，不是命令入口。

**How to apply（补）**：① 判「有没有」优先用**实际界面文案 + 用户截图 + 中文/本地化关键词**，
并在 IntlProvider 里查文案；② 英文标识符只用于「定位实现」，不用于「证明不存在」；
③ 命中数也要看上下文（同名不同义）；④ 结论写「未找到入口/未暴露到 UI」而不是「功能缺失」；
⑤ 报告里区分「UI 未暴露」「运行时已有」「已实测否决」三种状态；
⑥ 用户拿截图纠正时，先撤回错误结论并重写台账，不要只打补丁。
