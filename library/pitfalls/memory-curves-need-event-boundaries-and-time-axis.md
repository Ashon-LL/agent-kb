**经验**：长时运行的进程做内存/性能判读时，**事件和时间是两条轴，缺一条就会误判**。

- **只按时间**（按小时/按全天画曲线）：会把「应用重启、装机覆盖、进程换了一批」当成一条连续曲线，
  算出虚高的斜率，还会把「新进程从 51MB 起步」误读成「内存被回收了」。
- **只按事件**（只列重启/装机/配置变更时刻）：会丢掉段内的缓涨、闲置不释放、地板单调上升，
  漏判「使用量驱动的累积」。

**Why**：真案例——ZCode 11-06 全天 2731 个 30s 采样。第一版按小时切，得出
「16:50–22:48 从 51MB 爬到 1144MB、183 MB/h，地板不回落，疑似泄漏」。
用户指出当天装了好几次包、ZCode 被反复关闭重启，要求按事件看。改为按
**main pid 变化 + Program Files 装机文件 mtime** 切段后，真相是：

| 事件段 | 渲染层堆 | 斜率 |
| --- | --- | --- |
| 00:00–09:00（pid 20100，前日延续） | 51→133 MB | 9 MB/h |
| 09:00–10:44（重启 pid 14844） | 51→202 MB | 87 MB/h |
| 11:16–15:27（重启 pid 14924） | 51→712 MB | 145 MB/h |
| 16:49–22:48（重启 pid 15248） | 51→1373 MB | **68 MB/h** |

每段都从 51 MB 重新起步；两次装机时刻（10:56 asar、15:27 CLI）**堆无跳变**，
说明补丁没引入阶跃。原来那个 183 MB/h 是把 11:16 和 16:49 两批进程拼成一条线造出来的。
但**只有事件表也不够**：最后这段内部 20:18–21:18 堆恒为 1020 MB、DOM 节点/图片不动，
这个「闲置不释放」的形状只有回到段内时间轴才看得见。

**How to apply**：
1. **先找硬事件，别靠推测的边界**：应用重启看主进程 pid 变化（`[pid:N]` 日志）、
   配置变更看配置文件写入时间。装机**不要看产物 mtime**：`copy2` 打包会保留构建时刻，
   且安装目录常留最近两代 `*.bak-<stamp>`；取本次升级备份/升级前快照文件名，
   并以本代交付包准备时刻为下界排除旧备份（见 [[installer-completion-by-hash-not-mtime]]）。
   不要用「指标骤降」当事件证据——那既可能是重启也可能是 GC，会循环论证。
2. **事件轴上每段单独算三件事**：起点（新进程基线）、终点、段内斜率；
   再算**段内 30 分钟窗滚动最小值（地板）**，地板单调上升才是泄漏信号。
3. **时间轴上补齐段内形状**：闲置平台（值不动 ≠ 没问题，可能对象全可达）、
   峰值、突发块（停顿后首个增量样本要丢弃，见 [[burst-sample-after-idle-must-be-discarded]]）。
4. **两轴互校**：装机/重启时刻若指标无跳变 → 排除该变更引入阶跃；
   段内斜率若随使用强度变化（9/87/145/68 MB/h）→ 是使用量驱动，不是纯时间泄漏。
5. **计数器做跨进程对照**：同一份日志里 `projection.rows` 在 180–10702 波动而堆单调涨到
   1373 MB，就能把投影表从嫌疑里排除（[[measurement-must-verify-control-group]]）。
6. **验收标准写在双轴上**：不许用「刚更新完某一刻」或「全天均值」下结论；
   用「某个事件段内，连续使用 4 小时后，30min 窗地板斜率 ≤ X 且峰值 ≤ Y」。
