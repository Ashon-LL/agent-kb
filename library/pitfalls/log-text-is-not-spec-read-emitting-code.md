**经验**：日志文案、心跳措辞、代码注释里的通用描述，都是"给人看的字符串"，不是"系统行为的规格"。要判断一条日志代表什么，去读**发出它的那段代码**（grep 该文案 → 看它算的变量、触发条件、是否刷新计时）。汇报严格分三档并标注：实测（有命令输出/文件内容/码位）、推断（明说是推断、给置信度与反证条件）、未知（直说未知）。

**⛔ 外派文档加重条款（2026-09-16 用户立规）**：给 NPC/执行方的派单里，**未验证的推断一律写成"猜测、待你核实"，禁止用确定性根因句式**。执行者会把你的"根因链"当权威照修，锚定效应比你自己跑偏更贵——0916 炼制失控派单我把"预算是提示词被无视"钉成根因（标了"均为实测"但其实没验分发层），NPC 独立归因发现真根因是其上游："步骤循环根本没调用 run_refine_step、连预算提示词都没送达"，方向 D 也被它推翻。写派单时逐条自问：这条我有命令输出吗？没有就降级为猜测。

**Why**：0915 炼制步卡死，我连错三次都因拿字面当规格——① 看到心跳"模型输出中 本轮已持续 900s"就断定"模型连续思考 15 分钟"，实际读 `cli_lifecycle.py` 才知道那是"**无增量输出**已 900s"（last_line_ref 计时），意思正相反；② 搬 E1 注释"非流式+大请求体 60s 硬限制"当结论，被用户点破主链路早已全流式（0907-0913 五处流式化）；③ 半段日志里看到 `_refine/` 就判"lit-write 越界"，读全日志才知是炼制步自己的合法对账。流利的因果故事本身就是陷阱——它让我以为懂了，跳过验证，把纠错成本全推给用户。

**How to apply**：诊断任何"卡住/超时/静默"类现象，第一步 grep 出该提示语的代码看它的判据，别从文案脑补。任何解释链里出现"因为日志写了 X"→ 停下，先读发 X 的代码。

**同族实例：能力清单也不是可用性规格（2026-09-27 补）**——平台/接口给的**模型目录**只说明"名单位置存在"，不说明"能调"：本例某目录列 29 个模型，实测有 7 个返 `400 code=11102`（模型名不存在）——**目录与真实能力不一致**。反向更危险的是"文案暗示账号正常"：被账号级封禁的号，其**余额端点仍正常返回**（本例 4092 分），只有真实调用才拒（403/11140）。

⇒ 推论：**任何"存在性"证据（目录/清单/余额/状态字段）都不能替代一次真实调用**。判可用性只认「用目标能力实打一次并检查业务码」；把"清单里有"当"能用"、把"余额在"当"号健康"，都会漏判整整一类故障（见 [[quota-exhausted-vs-banned-distinguish]]）。

**同族实例：过程日志不是状态——「登录确认 ≠ 绑定完成」（2026-09-28/29 补，本条最贵的一个）**——
社区渠道插件的 QR 登录 API 在 confirmed 分支**只 return 凭据、不落盘**（落盘是渠道自己
那条路径 `channel.js:251 → persistWeixinLoginAccounts()` 干的）。我直接调编程 API 时那条
路径**根本不会跑**，于是：日志 `Login confirmed` 有了、界面「已扫码绑定」显示了、
退出码还是 0，而索引文件 `accounts.json` **根本不存在** ⇒ 渠道启动时无账号可挂载、
机器人完全不回话。⛔ **成功信号与真实状态相反、且零报错** —— 用户得自己发现"不能用"。

⇒ 推论二：**「已登录 / 已绑定 / 已授权」这类判定必须由落盘产物判定**（凭据文件、索引文件、
配置里真有的键），不能由过程日志、会话 state 或 API 的 return 值判定；并让**失败时退出码非 0**，
否则上层会把失败渲染成成功。
⇒ 推论三：调用第三方库的**低级 API** 时，要确认「高级流程里那些副作用（存盘/注册/通知）
谁负责」——低级 API 通常**只返回结果、不做副作用**。做法：grep 高级流程用到了哪些函数，
逐个确认。相关：[[config-field-name-is-not-spec-read-consuming-code]]。
