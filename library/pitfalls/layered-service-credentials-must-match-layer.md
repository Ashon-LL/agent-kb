**经验**：一个系统常由多层组成（前置网关 / 管理端 / 适配器），**每一层有自己的凭据**。凭据只对它所属的那一层有效——把 A 层的凭据配给 B 层的端口，表现是 **401 未授权**，而**不会**提示"你接错层了"。所以「端口」和「该端口对应的凭据」必须**成对确认**。

**Why**：2026-09-19 接入 WorkBuddy。该系统有两层：

- **管理端 :7864**（FastAPI）——持 `wbk_` 前缀密钥（`POST /api/keys` 下发），提供 `/v1/*` 路由，**带调用日志、积分记账、IP 管控、配额**。这是该接的那一层。
- **网关 :7863**（Go）——要的是它自己 `config.json` 里的 `api_key`，与 `wbk_` **不是同一个值**。直连它绕过管理端，无日志无记账。

我建 New API 渠道时 `base_url` 填了 **:7863**，key 填了**管理端的 `wbk_` 密钥** → 网关不认识 → 每次请求 `401 missing or invalid API key`。用户报「deepseek-v4.1-flash 连接失败」。实测同一把 key：打 :7864 → **200**，打 :7863 → **401**，一眼定位。

**更该避免的是这个过程**：我**早先手动 curl 验证时用的就是 :7864 且成功**，写渠道配置时却填成了 :7863。**验证过的正确值没有落到配置里**——验证和配置各写一遍，是这类错误的温床。

**How to apply**：

1. **建渠道/接上游前，先把拓扑画清**：有哪几层、每层监听什么端口、**每层的凭据从哪来**。特别警惕"两层都提供同样路径"（如 `:7864/v1/*` 与 `:7863/v1/*`）——它们看着一样，凭据却完全不同。
2. **凭据来源即归属**：`POST /api/keys` 下发的密钥属于**下发它的那个服务**；配置文件里的 `api_key` 属于**读那个配置文件的服务**。别按"都是这个系统的"想当然。
3. **判定接错层的快手法**：拿同一把凭据分别打候选端口，`200` 的那个就是它该去的层。一条命令就能出结论，别靠猜。
4. **验证过的值要直接复用，不要重打一遍**：手动 curl 成功时用的 URL/key，**复制进配置**，而不是凭记忆重填。或者在脚本里把"已验证的 base_url"定义成常量，配置与验证共用同一个来源。
5. **看错误码的语义**：`401` = 凭据不被这一层接受（可能接错层）；`404` = 路径不对（常见于 base_url 多带/少带前缀，见 [[newapi-base-url-never-carry-v1]]）；`403` = 认得出你但没权限。三者指向完全不同的修法。
6. **优先接带记账/日志的那一层**：多一跳换来的可观测性，远值那一跳的延迟——出问题时"没有日志"比"慢 200ms"贵得多。
