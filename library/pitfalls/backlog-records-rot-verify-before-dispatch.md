**经验**：项目自己的记忆库 / 债务台账 / TODO 里的「未做」「待办」「尚未派单」，**不等于现在还没做**。
拿它当下一批任务书的输入之前，**必须先在代码里复核每一条**——否则你会给执行方派一单「修一个已经修好的东西」，
轻则白跑一轮，重则为了贴合任务书去**推翻正确实现**。

## 实锤（2026-09-19，一次通读 + 逐条 grep）

任务：读完全部 69 份项目记忆，产出「接下来做什么」。结果**「未做」清单里 6 条全部其实已闭环**：

| 记忆里的旧口径 | 仓库实际状态（复核方式） |
|---|---|
| ⑤ `ticket_wall_clock_minutes` 名实不符、**尚未派单** | 已改名 `batch_wall_clock_minutes`，迁移代码在 `db/settings.py:193-202` |
| 「lit-search 出口**缺** PRISMA 数字对账门禁」 | 已实现：`delivery_audit_checks.py:380 scan_prisma_consistency` |
| 「vision **从未接入** literature_review 链」 | 已挂载：`delivery_audit.py:854 scan_vision_checks` |
| 「`screenshot_capture.py` 源码全库不存在（仅坏 .pyc）」 | 文件存在（9.0K） |
| 「`claude_code` 回退仍待拆，属独立后续单」 | 已拆（PR #77 merged） |
| 「门禁 6/6」 | 现 7/7 |

⇒ 若不做复核，**6 条里有 6 条会变成假任务**。

## 为什么会腐烂（三个机制）

1. **修的人 ≠ 记的人**：别人（或别的会话/别的 agent）修完只提了代码和 PR，没回头改台账那一行。
2. **文件是"页顶优先"结构**：`current-state.md` 这类基线页，**页顶有覆盖性更正、正文还留着旧值**；
   只读正文（或只读被索引指向的段落）就会拿到过时结论。⇒ **读到旧值先往上翻，看有没有「更正」块。**
3. **改名/重构让"名字"失效**：`grep 旧名字` 得 0 命中，容易被读成「没做」；
   实际是**改了名**（本例 `ticket_wall_clock_minutes` → `batch_wall_clock_minutes`）。
   ⇒ **按"机制"复核，不按"名字"复核**：搜它的消费点/迁移代码/常量，而不是只搜那个词。

## How to apply

- 从台账/TODO 取任务前，对每一条做**一次最小复核**：`grep` 它的**消费点**（不是名字）+ `ls` 它声称缺失的文件 + `git log --grep` 相关 PR。
- 复核结论**当场写回**（更新台账那一行或加更正块），否则下一个人/下一个会话还会踩同一个坑。
- 汇报时把复核结果**分两列**：「记忆说未做」vs「仓库实际」——让决策者看见差值，而不是转述旧口径。
- 与既有条目的关系：本条的复核对象是**自己的记录**；[[env-claims-must-be-reverified]] 的复核对象是**环境变更陈述**；
  [[ledger-audit-must-be-bidirectional]] 是**两套系统互核**。三条同族：**「陈述」不是「事实」，记录也会腐烂。**
