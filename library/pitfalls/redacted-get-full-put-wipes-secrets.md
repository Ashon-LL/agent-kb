**经验**：对带管理 API 的系统做"读-改-写"（GET 全量取回 → 改几个字段 → PUT 全量回写）是**静默破坏的高发形态**，本族已实测四类：

1. **GET 脱敏字段被抹**：GET 返回的敏感字段是掩码/省略的，原样回传即把凭据清空。→ 有脱敏就**绝不做全量替换写**，改用专用写入端点，或在写入体里显式重建敏感段。
2. **GET 返回结构判错**：以为 `data` 是字典、实际是**列表**，逐字段读取全部错位，拼出一个空/残缺的 PUT，把全站配置清空（GroupRatio 事故）。→ 读回后**先打印类型与键集**再构造写入体。
3. **参数白名单/最小写入体**：部分端点只收指定字段（如 `{id, models, model_mapping}`），带上 `status`/`type`/`groups` 直接报 Invalid parameters；空串则被**静默忽略**（以为改了其实没改）。→ 按端点最小字段集提交，改完立即回读确认。
4. **全量覆盖式写入无差异校验**：把"取回的对象"整体 PUT 回去，任何未识别的字段都可能被重置为默认。

**通用动作**：改前**先备份**（快照/DB 导出）；写入体只带要改的字段；写后**回读比对**关键字段；改凭据/认证类的，**当场用新凭据跑一遍完整真实流程**（如重新登录），别拿手里还没过期的旧 token 当"没坏"的证据（缓存令牌会把破坏掩盖很久才暴露）。恢复时优先复用应用自身的库函数，不手搓格式。

**How to apply**：任何"读配置 → 改 → 写回"的运维脚本与自动化渠道接入脚本，落地前按上面四类过一遍；批量配置操作要留**可回滚快照 + 写入前后字段 diff**。
