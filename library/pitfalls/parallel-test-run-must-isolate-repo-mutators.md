**经验**：给已有测试套件加并行（`pytest-xdist -n auto`）**不是加个 `-n` 就完事**。
先做一件事：把「会改写仓库工作树的用例」挑出来，让它们**独占**执行。

**辨识那类用例**（本次在这四类里各抓到实例）：
- **变异验证**：把真实源文件改坏 → 跑指定判据 → `finally` 还原；
- **构建产物断言**：产物缺失时现场 `npm run build` / `vite build`（写同一个 `dist/`）；
- 其它临时改 `package.json` / `Cargo.toml` / 配置再跑工具链的用例。

⛔ **「改完就还原」不构成安全**：破坏发生在**窗口期内**——并发时别的 worker 正好读到
改了一半的源文件（假红），或两个 worker 同时构建同一份产物（产物损坏）。

**落地形态（唯一稳的一种）**：
1. 给这类用例打标记（如 `@pytest.mark.mutates_repo`），标记注册在 `pytest.ini`；
2. 用**两阶段**跑：阶段 A `-m "not <标记>" -n auto --dist=loadfile`；阶段 B `-m <标记>`，
   **不带 `-n`**。互斥由**两个进程边界**保证（阶段 B 启动时阶段 A 的进程及子进程已退出）。
   ⛔ `--dist=loadfile` 只保证「同文件同 worker」，**不提供互斥**——别指望它。
3. ⛔ **不要把 `-n` / `--dist` 写进 `pytest.ini` 的 `addopts`**：变异用例内部常
   `subprocess` 起子进程 pytest（cwd=仓库根），`addopts` 会一并生效 ⇒ 每个子进程再开 N 个
   worker，用例自己的 `returncode == 0` 判据被拖垮/失真。并行只能是命令层选择。

**踩到的两个具体坑**：
- **兜底护栏也会假阳**：为防「进程被硬杀 ⇒ 源文件没还原」，我加了会话首尾哈希快照；
  初版只比对哈希，**没限定「本会话是否真的跑过变异用例」** ⇒ 与后台全量跑并存时，
  看到别的进程在改文件 ⇒ 误报「未还原」。修法：`pytest_runtest_setup` 里按标记置开关，
  会话尾只在该开关为真时判定。
- **跑测期间不许改工作树**：一边跑全量一边改文档，7 条「内容锁」用例当场红
  （文档改了、哈希清单还没写回）。判据与内容同批次变更时必须**先冻结、再跑**。

**度量（12 核）**：13m58s → 7m（阶段 A 3m17 + 阶段 B 3m43，≈2×）。⚠ 阶段 B 占 57%，
它是**串行成本**（变异探测本身就是这样设计的），不属并行化能吃掉的部分——
评估收益时要把它单独算，别按「总时长 ÷ 核数」估。

**守卫**（防约定漂移成假绿）：双向兜——① 命名约定（`*mutation*caught*` 必须打标记）；
② 静态扫描「函数体里写仓库根路径」的用例必须打标记；③ 例外名单（仅内存变异的用例）
要有**反证用例**，防止名单被用来藏真写手；④ 运行器阶段不变量（阶段 B 绝不带 `-n`）。
