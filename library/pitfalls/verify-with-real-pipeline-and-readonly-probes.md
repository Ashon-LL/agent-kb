**经验**：验证第三方应用"改对了没有"，最容易犯的错是**绕过它自己**——自己拼一个请求、自己按存储格式造输入。那样测的是你的猜测，不是它的行为。

**Why**：本次三个实测坑，一个比一个隐蔽：

- **持久化格式 ≠ API 输入格式**：把 DB 里 `conversations.content` 的原始格式直接喂给它的对话接口，必然 `400 inference request is invalid`——存储里含思考块和 `tool` 角色，真实管线要先转成它内部的 Message 对象。真实输入应当取自**运行时日志里的实际请求体**。
- **`test()` 类方法常常不返回正文**：AstrBot 的 `Provider.test() -> None`，不抛异常就算通过，拿不到出字内容。要证明"真的出字了"，得调真正的对话方法并读它返回结构里的文本字段（`text_chat()` → `response.result_chain.chain` 里的 `Plain.text`）。
- ⛔ **只读探针可能带写副作用**：某些配置类的**构造函数在缺键时会自动补默认值并回写配置文件**——你只想读一下配置，实际动了生产文件。

**How to apply**：

1. **先读签名**：看源码或 `inspect.signature`，确认方法有没有返回值、返回什么结构。别把"没抛异常"当通过。
2. **输入取真实样本**：从应用日志里抓它自己发出的请求体，而不是按存储格式手拼。
3. **探针默认只读**：实例化任何配置类/客户端类之前，先确认构造函数无写盘副作用；有副作用就改为直接读文件 + 手工解析，或先备份整个配置目录。
4. **断言终点可观测物**：出字内容、请求体里的键、文件内容——而不是"函数跑完了"或"启动日志没报错"。
5. 验证用的临时脚本跑完即删，别留在生产目录里被下一次误执行。
