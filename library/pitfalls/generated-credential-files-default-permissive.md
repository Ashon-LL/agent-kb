**经验**：**应用自动生成的凭据文件，权限通常是进程 umask 的默认值（多为 644）**，而同目录里由人工/其他工具创建的老文件可能是 600。两者混在一个目录时，**目录看起来"权限很严"，实际新文件对同机所有用户可读**。往凭据目录里加文件后，必须**逐个文件核权限**，不能只看目录。

**Why**：2026-09-21 给 WorkBuddy 池纳管第二个账号。新账号的 auths 文件由**管理端进程写入**，落成 **644**；而第一个账号的文件是**网关写的**、为 **600**。里面是**明文 refresh token / access token**——拿到就能冒充该账号。目录本身 `drwxr-xr-x` 看不出问题，是我逐个 `stat -c "%a %n"` 才发现的。属主是对的（都是容器 uid 10001），所以**功能完全正常、没有任何报错**——纯安全问题，没人会主动发现。

**How to apply**：

1. **往凭据目录加文件后，一律逐文件核权限**：`stat -c "%a %U:%G %n" <凭据目录>/*`（或 `ls -l`）。**别只看目录**——目录权限与文件权限是两件事。
2. **发现不一致就问"谁写的、为什么不同"**：本例是「网关写的 600 / 管理端写的 644」，说明**写入方不同、umask 不同**。知道这一点才能预判下次还会不会再出现。
3. **统一收紧到 600**：`chmod 600 <凭据目录>/*.json`。属主保持不变（容器要读）。
4. **改完必须回读验证应用仍能读**：改权限可能踩"bind mount 属主/权限"坑（见 [[bind-mount-owner-must-match-container-uid]]）。本例改完重查账号列表仍为 2 个、`/healthz` 正常才算通过。
5. **把"新账号/新文件"纳入纳管清单**：新增账号、新增组件、恢复备份之后，都要重跑一次权限核对——这是**每次都该做但很容易忘**的一步。
6. **顺带检查同族**：`data/` 下的 state.json、DB 文件、`.env`、config.json 同属凭据类，一并核；本例 config.json 已是 600。
