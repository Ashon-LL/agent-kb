# 最小面原则会退化成「发现了但不修」

**现象**：Agent（或你自己）排查出真缺陷后，因为「保持改动面最小 / 不扩大范围」而
只报不改、或改一半留个 TODO，缺陷就烂在那里。实测：`comp-code` 这个问题拖了 3 天 4 轮
（每轮都"发现"了，每轮都"先不动"）。

**为什么会发生**：最小面原则本来是**排序规则**（同样要改时先改影响小的），
但很容易被当成**筛选规则**（有别的更要紧的就先放着）。而"别的更要紧的"永远排队，
于是"次要"的永远不动。

**代价**（实测过的两种，都很贵）：
- 留在代码里 ⇒ 下一个维护者重新发现一遍；交接文档里变成"已知遗留"。
- 变成隐性地否决：明明已经证明是真问题，却因为"这轮不碰它"而被当成不重要。

**做法**：
1. **排序用最小面，筛选不用**。要不要修，看「真不真」（有没有一手证据），
   不看「这轮方不方便」。有证据的真缺陷 = 本轮就修。
2. **"范围外"要写进交接，而不是留在代码里**。真要留，写清「已定因 + 为什么这轮不做
   + 什么条件下做」，并进 `docs/dispatch/` 或 INBOX 派活板（能被下一个人捡起）。
3. **复算时看到红就问"这条是真缺陷还是用例自己的问题"**，别用「测试有问题所以不算」
   一句话糊过去。本仓就有过两例：用例硬编码 POSIX 路径在 Windows 上必红（该修用例）、
   用例写死字节数在多字节文本上假红（该修用例）——但也有"测试抓到了真缺陷"（该修产品码）。
   **两种都要处理，只是修的地方不同。**
4. **把「先不动」写成待办交出去**，而不是记在脑子里。派活板（`docs/dispatch/INBOX.md`）
   就是干这个的。

**一句话**：*最小面是"先修哪个"的规则，不是"能不能不修"的许可。*
