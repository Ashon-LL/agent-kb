「不引入依赖」的直觉在**有强规范的对象**上是错的。我为了给二维码做无依赖兜底，
手写了纯标准库的 QR 编码器（byte 模式 / M 级 / 自动版本），与 `segno` 的
输出矩阵**逐格对账差异 836/1681**（v6 码，边长 41）——**编码是错的**，
只是 SVG 照样渲染得像二维码，肉眼完全看不出来。

**如果我没做那个对账，就会交付一个永远扫不出来的二维码**，而且它长得完全正常。

## 教训

1. **强规范对象不要自造编码器**：QR/条码/PDF/OOXML/压缩/加密这类，
   规范细节（掩膜评分、RS 纠错分块、格式信息 BCH、交织顺序）错一个就废，
   而**失败是静默的**（渲染正常、扫不出来）。
2. **必须做「与成熟实现对账」**：不是断言"我生成了 SVG"，而是
   **逐格比对矩阵**（或解码回读原文）。这一步是发现 bug 的唯一途径。
3. **依赖缺失的正确解法是多级兜底**，不是自己实现：
   ```
   ① 主库（项目原有，如 segno）
   ② 备库（另一实现，如 qrcode——纯 Python，SVG 工厂无需 Pillow）
   ③ 返回空串 + 明确错误，让上层报可诊断信息（绝不静默）
   ```
   两个库都写进 `requirements.txt`。
4. ⛔ **别假设「requirements 写了就等于装上了」**：安装区/发行包的运行时
   包集**常不受仓库 requirements 控制**。本例 `segno>=1.3` 明明白白写在
   requirements 里，安装区 runtime 就是没有 ⇒ 功能静默降级
   （接口返回空 SVG；同项目的另一功能「检查点二维码」也因此一直报
   「segno 未安装」，谁都没发现）。
   ⇒ 结论：**运行时依赖要有代码级兜底 + CI/启动自检**，不能靠 requirements 声明。
