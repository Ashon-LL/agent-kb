**经验**：更新脚本里「检测到目标应用在运行就结束进程」这一步，**必须同时满足两个条件**才允许杀：
1. **目标路径确实是当前安装目录**（拿定位函数的结果比对目标文件的祖先目录，而不是只看进程名存在）；
2. **确实有文件要写**（先算现有文件哈希与目标哈希，不同才叫有变更）。

只按进程名判断（`taskkill /IM App.exe /T /F`）会带来两个后果：

- **自测时把用户正在用的实例杀掉**。用 `-Target <临时目录>` 做写入测试是很自然的做法，但脚本只看进程名，照样杀真身。用户视角就是「应用莫名其妙退出了，我又点开一次」，连续发生多次后会当成崩溃去查。
- **杀掉宿主自己的会话**。如果 agent 正跑在这个桌面应用里，`taskkill /T` 连宿主一起带走，当前工具调用被中断（表现为"命令没返回就断了"），而脚本已经部分生效 ⇒ 归因更容易跑偏。

**Why（为什么特别隐蔽）**：
- `taskkill /F` 是硬杀，**被杀的进程没有任何日志**：日志停在最后一条正常记录，没有错误行、没有 dump、没有 Windows 应用程序错误事件 ⇒ 和"崩溃"在未取证时**长得一样**；
- 用户手动重开的间隔（几秒到一分多钟）会打乱"崩溃 → 重开"的因果推理，容易归因到"另一个工作区在跑大脚本"；
- 部分生效：目标确实被杀了，所以"看结果"不能判断脚本是否正确。

**How to apply**：
1. 杀进程前先做「**是不是真身**」判断：`Test-IsLiveInstall($target)`（目标祖先目录 ∈ 定位函数结果），以及「**有没有活要干**」（对比现有哈希）；
2. 提供显式逃生开关：`-KeepRunning`（不杀）、`-ForceKill`（临时目标也强制杀，慎用）；
3. 写盘前再加一道保险：真要写、且目录被占用 → **报错退出**而不是硬写；
4. 无变更时顺带跳过"启动应用"，避免重复拉起。

**判据（怎么区分「被外部杀了」和「真崩溃」）**：
- 被外部硬杀：旧进程日志**停在一条正常 RPC 中间**、无错误行、无新增 dump（看转储目录 mtime）、无 Windows Application Error 事件、重启的进程**内存也正常**（不是 OOM）；
- 真崩溃：有新 dump / minidump、有 `js_heap_exhausted` 之类的判据、事件日志有记录。
- 想定位"是谁杀的"，先枚举**自己跑过的所有 destructive 命令的时间点**与日志截断点对齐——2026-10-29 这次五个重启点（00:22:19 / 00:23:53 / 00:33:24 / 00:35:54 / 00:40:27）全部对上自测运行时刻，而修掉脚本后再跑同一条测试（00:43:37）**没有产生任何重启**。
