**经验**：**本机到云端的 SSH 通道**与**云端容器里任务的执行**是两件独立的事。
本机心跳连续 FAIL ≠ 环境死、更 ≠ 任务停。

**实测事实（这次踩的）**：
- 本机保活心跳从 `02:54` 起连续 FAIL（`hb#45` 起，累计 84+ 次），我据此**报了两个错误结论**：
  ①「工作区被平台提前关闭」②「主实验（250 题）没跑完，需要重跑」。
- 真相：容器内的执行者**完全不受影响**，一路干到 **04:18**（环境真正关闭时刻），
  并把主实验跑完（**2301 调用 / 1.24M tokens**）+ 论文 43 页 + 视觉检验 + 炼制全量归档，
  期间共 **4 次 push**（`20625da` / `ce0b563` / `d6b9c15` / `3b264d7`）。
- 我是**事后 `git fetch` 才发现**远端多了 4 个提交、任务早已完成。

**为什么容易误判**：心跳是「本机→云端」的单向探针，断的原因通常在本机侧
（本机网络/防火墙/WARP/睡眠恢复），与容器无关；而容器里跑的进程（CodeBuddy 会话、
实验跑器）由云端独立调度，**不需要本机 SSH 持续在**。

**How to apply（判据正序）**：
1. **判「任务是否完成」→ 看 git 远端**：`git fetch origin && git log --oneline origin/<branch> -5`
   （这才是产出的权威落点，⛔ 不是本机 SSH 通不通）。
2. **判「环境是否还活着」→ 看平台侧**：`cnb workspace list-workspaces --slug <repo>`
   的 `status` 与 `duration`（`duration` 换算成小时，跟 18h 上限比）。
3. **本机心跳 FAIL 只作一条信息**：说明本机通道有问题（先查本机网络），
   ⛔ 不得直接推成"环境死/任务停"。
4. 想确认容器内实况（还能连时）：`ssh ... 'ps aux | grep -c python; date'`；
   连不上就**别硬推结论**，改写「本机 SSH 不通，云端状态未知，待查 git/平台」。

**代价**：我因此向用户误报了「任务没跑完、需要重启重跑」——差点让用户为**已经完成的工作**再付一次钱。
