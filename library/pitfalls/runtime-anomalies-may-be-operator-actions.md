# 运行态异常也可能是用户造成的——别默认它在报故障

**现象**（2026-10-05，用户当面纠正）：
会话交接核对时我发现安装区后端进程没了（18088 无监听），当场写成
「**一处异常，如实报告**：后端进程不在运行……可能是之前某次同步的重启窗口
或软件壳被关过」，并顺手用脚本把它拉了起来。
用户回复：**「发现不在运行，有可能是我关了。很多异常有可能是我造改动的，你知道吗」**

**问题出在哪**：
- 这是**共用环境**（用户 + 我 + 其他 Agent 都能启动/关闭/修改），
  但我的叙述把「与我预期不符」直接升级成「异常」，暗示对象可能有问题；
- 我随即执行了一个**状态变更动作**（重启进程），而没有先问一句
  「这是不是我该恢复的」——用户如果是**有意关闭**（省电 / 手动调试 / 换配置），
  我的"恢复"恰好是破坏他的意图；
- 同类还有：文件/配置与记忆不符、工作树里冒出的改动、DB 里的值变了、
  某个开关与上次不同——**它们都可能是用户的操作痕迹**，不是 bug 现场。

**怎么防（三条）**：
1. **叙述去定性**：只说事实与范围——「18088 当前无监听（未确认原因）」，
   ⛔ 不写「异常 / 崩溃 / 出问题了」；把成因留给下一步核实，别替它下结论。
2. **恢复态动作先问或先说明**：对「把它拉起来 / 重跑一遍 / 重置状态 / 覆盖配置」
   这类**会改变环境当前状态**的动作，先确认「这是有意为之还是需要我恢复」；
   用户不在场时，宁可保持原状并报告，不擅自修复。
3. **核实顺序**：先查「是不是用户/其他 Agent 干的」（近期人为操作、mtime、
   会话交接记录），再查真实故障。这与另一条通用纪律同源——
   **「发现与预期不符」先怀疑观测口径或他方操作，最后才归因于缺陷**。

**与已有条目的区分**：
- `report-what-you-did-not-what-you-meant-to-do` 管的是**我自己的**虚报
  （"以为在做"写成"已生效"）；
- 本条管的是**别人的操作**被误读成故障——方向相反，同样禁止。

**关联**：[[user-instruction-is-not-evidence-of-no-dependency]]（用户动过的东西，
不要拿"他让删了"当"没人用"的证据）；项目内对应记忆：工作区多方共用
（非我造成的改动只报告、不追查不提交）。
