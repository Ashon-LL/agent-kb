**经验**：查文档不能只查「字段名」，要查**该字段对该步骤类型**的定义。
同名同位置的字段，在通用步骤与特殊内置步骤上可能是两件事。
而且——**同一个字段可能同时管两件事**：CNB 的 `timeout` 既设「任务总时长」，
**也**设「无输出超时」，两者同值，调它会同时松掉两个保护。

## 症状（真实案例）

`.cnb.yml` 里给一个 `type: npc:go` 的步骤声明了 `timeout: 4h`，
注释里信心十足地写着：

```yaml
# 任务级超时（官方：Job 默认最长 2h，声明 timeout 后按其值执行，上限 12h）。
# 故声明为 4h（用户指定）……
timeout: 4h
```

**结果没兑现**：该工单里一条卡住的脚本在 **1h52m** 后被 SIGKILL（exit 137），
容器随后销毁，会话中止 —— 不是 4h。

用户直接质疑：「**明明允许的是四小时，为什么仍然是两小时就停了？**」

## 真相：两处官方原文

**`npc:go` 文档「超时」节**（决定性）：

> 所在 Job 声明的 `timeout` 作用于 Agent 的**每一次工具执行**（如 bash 命令）：
> 单次工具执行超过该时长、或连续无输出达到该时长，会被强制中断并以执行失败返回给 Agent；
> **未声明时取默认值（无输出超时 10 分钟，单次最长 2 小时）**。
> **Agent 会话本身不设整体超时**，整体时长受流水线超时（20 小时）约束。

**超时策略页**（决定性的第二处原文）：

> 任务（Job）可通过声明 `timeout` 自定义超时，未声明时采用如下默认值。
>
> **对于 `npc:go` 等 Agent 任务，`timeout` 作用于 Agent 的每一次工具执行（如 bash 命令），
> 而非整个 Agent 会话；会话整体时长仍受流水线超时约束。**
>
> **无输出超时**：若 Job 连续 **10 分钟**无任何输出，将触发超时。
> 若声明了 `timeout`，则**无输出超时时长与配置值一致**。
>
> **最大超时时间**：Job 默认最长执行 **2 小时**。
> 若声明了 `timeout`，则按该值执行，最大不超过 **12 小时**。

**语法手册 `timeout` 条**：

> 设置单个任务的**超时时间和无输出超时时间**，默认单个任务的超时时间为 2 小时，
> 最大不能超过 12 小时，**无输出超时时间为 10 分钟**。**对脚本任务和插件任务有效。**

⇒ `timeout` 在**脚本/插件 Job** 上 = 「任务总时长」**且**「无输出超时」（**一个字段两件事**）；
在 **`npc:go`** 上 = 「**单次工具执行**的时长」（且沿用 10min 无输出默认，除非显式声明）。
**两者不是一回事**，而我把前者的语义套到了后者上，还在注释里标了「官方文档原文」——
这是**假引用**，比没写注释更坏。

## 附带教训 A：调大「总时长」会**连带松掉无输出保护**

官方：「若声明了 `timeout`，则无输出超时时长与配置值一致。」
⇒ 给脚本 Job 写 `timeout: 4h`，实际同时得到「最长 4h」+「连续 4h 无输出才超时」。
默认的 **10 分钟**无输出保护被悄悄抹掉了 —— 一条**静默**挂死的命令会拖满 4h
而不是 10min 就被掐。**求长窗口时别忘了这一副作用**，并在脚本内自加 `timeout -k`。
（如果是**刷屏**型卡死则无输出超时不生效，只能靠总时长 —— 两种卡法要两种兜底。）

## 附带教训 B：二选一的错误文案不能当单一结论

## 取证手法（判断「这是我以为的那个上限吗」）

别只看错误文案，要**多取几层证据**：

| 证据 | 本轮取值 | 说明 |
|---|---|---|
| stage `startTime`/`endTime` | 11:55:11 → 13:56:12 | 会话总时长 121.01 min |
| 最后一条**命令**回显时间 | 12:03:15 | 命令真正开始 |
| 该命令被杀时间 | 13:56:10 | 由下一条 agent turn 的 `started` 时间反推 |
| 该命令**自报**时长 | `Finished, code: 137, duration: 1h 52m` | 与上两行之差 112.9 min 吻合 |
| exit code | **137** = 128+9 = **SIGKILL** | 被杀，非正常退出 |
| 被杀后的动作 | `cat …` → `Error response from daemon: No such container: <sn>` | **容器已销毁** ⇒ 级联中止 |
| **对照组**（另一单 success） | 最长单命令仅 8 min、零个 137，会话总时长却 **99.6 min** | **证明"会话总时长"不受 2h 卡** |

对照组是关键：它把「会话总长 2h 上限」这个假设**证伪**了，
把问题定位到「**单条命令**」这一层。

## 附带教训：二选一的错误文案不能当单一结论

CNB 的最终错误文案是：

> `Agent aborted: the build environment terminated unexpectedly,`
> `or the pipeline exceeded its max run time (2h).`
> 「Agent 已中止：构建环境异常终止，**或**流水线超过最大运行时长（2h）。」

它把两个原因**用「或」并列**。我第一次直接读成「超时（2h）」，但实测证据
（容器 `No such container`）指向的是**前一个分支**：构建环境异常终止。
⇒ 遇到「A，或 B」式文案，**必须先取证判断落在哪个分支**，不能挑自己顺眼的那个。

## ⛔⛔ 第二次修正：**「被掐在 2h」与 timeout 配置确实无关**（原因见下文第四次修正）

⚠️ **本节的「真因 = 裸 `wait`」表述已被推翻，保留作过程记录。**
真因是**平台硬边界**；裸 `wait` 只是「让这条命令永久挂起、从而撞上边界」的**触发方式**，
**不是**「被掐」的原因。两者是「谁把它推到边界」与「边界在哪」的区别。

用户追问「这个时间限制到底解决了没有、明明之前就能解决的」后，
我**反查了全量构建记录**（`cnb build get-build-logs --event api_trigger_npc`），拿到横向对照：

| sn | 日期 | 当时 `npc:go` 的 timeout | 实跑时长 | 结论 |
|---|---|---|---|---|
| `cnb-sdo-…` | 09-16 | **未声明**（= 官方默认 **2h**） | **121.67 min** | ✅ **success** |
| `cnb-eke-…` | 09-18 | 声明 **6h** | 121.12 min | ❌ error |

**未声明 timeout（名义只有 2h）的那单跑了 121.67 分钟**；
声明 6h 的那单反而 error，**两者只差 0.55 分钟**。
⇒ **改 `timeout` 数值解决不了问题** —— 因为它管不到真正生效的那层（见第四次修正）。

**真因（runner 原始日志实锤）**：失败单的任务书里有一条 heredoc 脚本：

```bash
node upstream_slow.mjs 59995 12000 > up-slow.log 2>&1 &
SLOWPID=$!
( timeout -k 5 60 node ... agent --local ... ) &
( timeout -k 5 60 node ... agent --local ... ) &
wait                       # ⛔ 裸 wait：等**所有**后台任务，含常驻假上游
kill $SLOWPID 2>/dev/null  # ⛔ 排在 wait 之后 ⇒ **不可达**
```

日志实证：`[00:08:10] $ cat > run_lock.sh <<'SH' …` → `[02:01:05 +1.9h] exit code: 137`，
即**单条命令**跑满 1.9h 被 SIGKILL，随后 `No such container`（容器销毁）⇒ 会话 error。

⇒ **「之前能跑 121min 成功」不是「以前超时配得大」，是「以前那条命令没有裸 `wait`」。**

### 方法教训（比技术结论更重要）

1. **别顺着「用户/自己的假设」往下答** —— 两轮都在调 `timeout` 数值，而病根在脚本里的 `wait`。
   ⛔ 至少要用一次「**反面证据**」检验当前假设：本例只要问「有没有跑超 2h 还成功的单？」
   就能立刻证伪。
2. **平台类问题先拉全量历史记录做横向对照**，别只盯单个失败单纵向推理 ——
   `get-build-logs` 一次返回上百条，里面自带对照组。
3. **别把「错误文案里的数字」当上限来源** —— 文案说 2h，实际有单跑 121.67min 成功。

## ⛔⛔ 最终结论（同日第三次修正）：平台侧**确有约 2h01m 硬性中止**；「成功反例」是巧合

我第二轮据此断言「被掐与 timeout 无关、不是被掐」—— **方向对了一半，但把「巧合」当了「反例」**。
用户当场指出：「**`cnb-sdo` 能超过 2h 可能是巧合**」。逐行读原始 runner 日志后确认**用户是对的**：

**`cnb-sdo`（121.67 min, success）的真实末尾**：

```
[01:59:51] $ cd /workspace && grep … ; python3 scripts/release_check.py | tail -20
[02:01:03  +1.2m]  exit code: 137, signal: -1          ← 同样被 SIGKILL
[02:01:06]         Error response from daemon: No such container: cnb-sdo-…-001
   → 其后 8 条命令（含 `echo hello`、`true`）全部 No such container / exit 1
```

它**也**在 `02:01:03` 被 SIGKILL、容器**也**被销毁；之所以记 success，
只是因为**碰巧在被销毁前把产物写完并推送了**。而 `cnb-eke` 在 `02:01:05` 被同样处理，
只是它死前没留下可汇报内容 ⇒ error。
**两次独立事件的被杀时刻相差 2 秒** ⇒ 平台侧确有约 **2h01m** 的硬性中止。

⇒ 正确表述：
1. **[实测] 平台侧有约 2h01m 硬性中止，与 `timeout` 声明无关**（声明 6h 照样被掐）。
2. **[实测] 那个「success 反例」是巧合，不能用来证伪上限存在。**
3. **[实测] 全量记录中没有任何「跑满 2h 仍正常收尾」的单。**

### 方法教训（**本轮最贵的一课**）

- ⛔ **别把「状态为 success」当作「没被中止」的证据** —— 状态码只说明「收割时有没有东西可汇报」，
  不说明「过程有没有被强杀」。**必须读原始日志里那条 `exit code: 137` 与 `+1.9h`**。
- ⛔ **用反面证据证伪假设时，反面案例也要挖到「机制层」才算数** ——
  我只看了「status=success + 121min」就宣布证伪，没看它最后一分钟发生了什么。
  **同一个 137，两种结局**：临死前推完了 = success，没推完 = error。
- ⛔ **「时刻相差几秒」这种巧合是强证据**：两次独立事件都落在 `02:01:0x`
  ⇒ 硬性边界，而非随机波动。

### 真正的对策（配置项无能为力时）

既然边界不可配置，**唯一可靠手段是让单条命令永不无限等待 + 尽早留痕**：
禁裸 `wait`、整段 `timeout -k`、`trap ... EXIT` 释放常驻进程、单条命令 ≤5min、
**增量推送**（已推的能留下，没推的全丢）。清单见仓库 `docs/dispatch/NPC-SHELL-CHECKLIST.md`。

## ⛔⛔⛔ 上限来源已取证定位（同日第四次修正）：**`maxPipelineRunTime: 2h` / `CNB_PIPELINE_MAX_RUN_TIME=7200000`**

前一轮我把「约 2h01m 硬边界的来源」标为「未知」。现已**拿到两处实锤**——
**同一个值的两个出口，位置不同、形态不同**：

| 位置 | 形态 | 取值 | 取证命令 |
|---|---|---|---|
| **prepare stage**（pipeline init 段） | `maxPipelineRunTime: 2h` | 人类可读 | `cnb build get-build-stage --sn <SN> --pipelineId <SN>-001 --stageId prepare`，读 `data.content` |
| **runner 容器内**（env dump） | `CNB_PIPELINE_MAX_RUN_TIME=7200000` | 毫秒 | `strings <runner日志>.bin \| grep -o 'CNB_PIPELINE_MAX_RUN_TIME=[0-9]*'` |

prepare stage 原文（实测输出片段）：

```
"Pipeline actual limit cpus: 8, memory: 16","maxPipelineRunTime: 2h","quota size: {...}"
```

⛔ **取证踩坑（我在此绕了两轮）**：我最初在三份 **runner 日志**里 grep `maxPipelineRunTime`
得 **0 命中**，就以为「这个字段不存在/用户看错了」。
**错在查错了日志层** —— 它印在 **stage 级（prepare）日志**里，不在 runner 级日志里。
⇒ **方法教训：查「平台限制声明」要查 stage 级日志（prepare），不是 runner 级日志。**
（反之，查「实际执行环境与进程行为」才看 runner 日志。**两层日志各管一段，别混查。**）

两份**不同构建**的 runner 日志独立命中同值 `7200000`：

| 日志文件 | 对应 sn | 命中值 |
|---|---|---|
| `1789715398724-mzna8l6.bin` | `cnb-l7g-1k2msrcvb` | `7200000` |
| `1789639674780-m369k4u.bin` | `cnb-ds8-1k2nd9mhr` | `7200000` |

⇒ 与实测被杀时刻 `02:01:03` / `02:01:05` **精确吻合**（2h + 数十秒处置延迟）。
**「约 2h01m」不是估算，是 7200000ms 这个确定值 + 处置延迟。**

⛔ **注意与另一个同族取值的混淆风险**：第三方检索结果中出现过
`CNB_PIPELINE_MAX_RUN_TIME=3600000`（= **1 小时**），语境是「**系统内置 CodeBuddy** NPC
的默认档位」（平台托管、仓库改不了）。⇒ **同一个变量名，值随 NPC/档位不同**；
**本仓实测值是 7200000，不要拿 3600000 的推断来套本仓。**

### 关于「声明 timeout 能否放宽」——两条限制**并存，不矛盾**

官方 `npc:go` 超时专节原文（决定性）：

> 所在 Job 声明的 `timeout` 作用于 Agent 的**每一次工具执行**（如 bash 命令）：
> 单次工具执行超过该时长、或连续无输出达到该时长，会被强制中断并以执行失败返回给 Agent；
> 未声明时取默认值（无输出超时 10 分钟，单次最长 2 小时）。
> **Agent 会话本身不设整体超时，整体时长受流水线超时（20 小时）约束。**

⇒ **[推断]** 存在**两条并存的限制**，作用对象不同：
1. **`timeout` 放宽的是「单次工具执行」上限**（脚本 Job 上则是 Job 总时长上限）
   —— 官方明确可放宽至 **12h**；
2. **`CNB_PIPELINE_MAX_RUN_TIME=7200000` 约束的是「流水线整体」** ——
   **在 `npc:go` 这个场景下它就是那个先到的天花板**，且**本仓无法通过 `.cnb.yml` 改**。

⇒ **[事实，20260919 用户裁定]** **脚本 Job 同样会被 2h 掐**。此前我标的是「未验证 —
从未测过纯脚本 Job」；用户明确告知**已反复验证过会被超**（`20260919`：「**肯定会被超，之前反复验证过的**」）。
⇒ 故本条**不再是未知项**：`CNB_PIPELINE_MAX_RUN_TIME=7200000` 是**整条流水线的硬天花板**，
**与步骤类型无关** —— 脚本 Job 声明 `timeout: 4h` 也**照样在 2h 被掐**。
⇒ **唯一对策 = 任务自身有界 + 开工即推/增量推送**（别指望靠 `timeout` 或改 Job 类型绕过）。

> ⛔ 证据来源纪律：本条为**用户第一手裁定**（他做过对照实验），非我的实测复现。
> 我的全部取证只覆盖 `npc:go`。按「不许乱猜测」纪律，此处**如实标注来源**，
> 不冒充成我的实测结论。

### 附带证伪：「2h 被杀是无输出超时」❌

第三方分析主张「很多『跑了两小时被杀』其实是**无输出超时**，而非总时长」。实测**证伪**：

`cnb-eke` 日志时间戳密集度 —— 静默段长达 **1.9 小时**：

```
[00:08:06] …（正常输出）
[00:08:10] $ cat > /tmp/d17/run_lock.sh <<'SH'   ← 最后一条有输出的命令
[02:01:05  +1.9h] exit code: 137, signal: -1      ← 中间 1.9h 零输出
```

若真是无输出超时，它应在 `[00:18:10]` 前后（+10min）就被回收 —— **但它活到了 2h 整**。
⇒ 判据是**总时长**，不是无输出。**该假设不成立。**
（旁证：全量日志中 grep `no output` / `无输出` / `idle timeout` 均 **0 命中**，
平台未按无输出超时口径报错。）

## 仍未确证的（按纪律标「未知」）

1. **`CNB_PIPELINE_MAX_RUN_TIME` 能否被 `.cnb.yml` 覆盖 —— ✅ 已定论：不能。**
   已知它不是普通语法手册字段；第三方建议的 `timeout: 6h` 写法**在本仓 `npc:go` 上实测未生效**
   （`cnb-eke` 声明 6h 仍在 2h 被掐）。**脚本 Job 同样被掐**（20260919 用户裁定，见上）。
2. **该值是否会随账号档位/预算变化，未知。** 官方 NPC 曾提及「动态管控 / 绑定预算可提升用量上限」，
   ⛔ **无凭据，不予断言。**

## 正确做法

- **查字段前先确认步骤类型**：通用步骤（`script`/插件）与内置步骤
  （`npc:go` 等）字段语义可能不同 —— 优先读**该内置步骤自己的文档页**
  （本例 `internal-steps/npc/go.html` 的「超时」小节），不要只读语法手册。
  ⚠ **两处文档可能互相矛盾**：语法手册说「对脚本任务和插件任务有效」，
  超时策略页却补了 npc:go 的专节 ⇒ **以更具体的专节为准**，并在注释里**两处都引**。
- **分清「哪个超时是我能改的」**（本例三层，互不替代）：
  | 层 | 能改吗 | 管什么 |
  |---|---|---|
  | 流水线超时 **20h** | ❌ 平台级，文档未给配置入口 | 整个流水线 / Agent 会话整体 |
  | Job/步骤 `timeout` | ✅ 本仓 `.cnb.yml` | 脚本 Job＝总时长+无输出；npc:go＝单次工具执行 |
  | 脚本内 `timeout -k` | ✅ 代码 | **唯一能保证"这一段有界"的手段** |
  ⛔ 「会话被掐在 2h」若真是平台级，**改 yml 无用** —— 别把力气花在改不了的那层上。
- ⛔ **别在注释里用「官方文档原文」字样去包装自己转述/外推的语义** ——
  真引用要给得出出处页；转述要标「转述」。
- **两个不同语义的同名字段，在同一个文件里要互相交叉引用**，
  否则下一个人（或下一个我）还会再套错一次。
- **别指望平台字段给长跑命令兜底**：能长跑/可能卡住的命令
  **一律在脚本内自加 `timeout -k <N> <M>`**。

定义是什么？」—— 答案不在字段名里，在该步骤的文档页里。
