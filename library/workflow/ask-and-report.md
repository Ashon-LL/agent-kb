## ask-with-options-early-never-at-end

**经验**：需要用户拍板时用 AskUserQuestion 同批给 2-4 个选项（推荐项排第一标"(推荐)"、每项一行取舍说明、保留"其他"自由输入）。要问就当场问，不要憋到总结末尾。选项要可执行（"全清/只改X/不再改"这种粒度），不要问"要不要继续"这类空转问题。

**Why**：把问题留到收尾才抛，等于让用户在一堆已完成动作之后才发现要决策。用户原话"我真服了你，问我不要在最后才问我。你直接提供给我多选项"——出现"我真服了你了"信号时不要再解释、不要把问题抛回去，直接给选项或直接动手。

**How to apply**：同批已落地案例：收尾时给"全清（推荐）/只改§5/不再改"三选，用户选全清→据此清掉3处残留提及。需要拍板时当场用多选项摆出来，独立成段，不伪装成汇报的一部分。

## never-pad-reports-with-desired-state

**经验**：成果汇报里只放已发生的事（做了什么、验证结果、有什么风险）。缺什么就说缺什么，不要顺手挂一个"你要不要顺便决定X"。真需要用户拍板时当场用多选项摆出来，独立成段，不伪装成汇报的一部分。

**Why**：报本轮成果时在末尾加了一句"有两处你看到时也可以现在决定要不要我做"——属于把未定事项塞进成果汇报，读者会以为"这是已定的事/我已经点头了"，实际什么都还没定。更糟的是让汇报失焦：成果被一条待办尾巴污染。

**How to apply**：派单前分清产品缺陷（对方的活）vs 我自己的工具/流程债（我自己收拾）。把工具债塞给对方被纠正"这个就不是人家的任务"。需要拍板时当场用 AskUserQuestion 独立成段，不夹在成果汇报末尾。

## explain-dont-advise

**经验**：当用户明确表达「你别瞎建议」「把东西说明白」「我是个原始人」时，他要的是**解释**，不是**方案**。
一句话：先回答"这东西现在是什么、为什么这样"，不要顺手接"建议你下一步做 X / 可以考虑 Y / 更好的做法是 Z"。

**Why**：建议等于把决策成本推回给用户，而且多数建议建立在用户没说完的上下文上。
在长时间排障会话里，用户已经听了十几轮"建议"，真正缺的是**能自己判断的模型**：
哪个数是真的、这个数意味着什么、我看到的界面变化对应后台哪一步。
给不出这个模型，建议越多越像在乱试（本会话里就出现过"建议改参数 → 无效 → 再建议另一个参数"的循环）。

**How to apply**：
1. **先定义再回答**：把用户看到的现象翻译成后台机制（"你往回翻 → 每翻一次后台拉 200 行，旧的不会删，所以滚动条变长"）。
2. **数字要能对上现象**：说"在扩大"就给出扩大的那个量（rows 从 244 涨到 X），不要让用户自己猜。
3. **不给建议**：只在被问"那怎么办"时给，且给的是**选项+代价**，不是单一最优解。
4. **不夸大也不兜底式承诺**：说不出原因就说"不知道，我需要测什么"。
5. **格式服从理解**：短句、列表、表格都行，但避免自创代号（A/B 方案、P0/P1 除非用户已经知道）。
6. **别用"建议/可以/不如"开头**；用"现在是这样 / 原因是 / 这个数字表示"开头。

## no-sycophantic-agreement-openers

**经验**：回答里删掉一切确认式开场（"你说得对""问得好""这个担心成立"）。被用户纠正时，正确结构只有三步：① 一句认领错在哪 ② 立刻给修正后的事实/结论 ③ 继续干活。需要用户裁定时直说"我倾向 A，理由是 X，你定"，不要先把"你说得对"当润滑剂。

**Why**：0915 会话我每次被质疑（炼制耗时、工具调用、流式与否）都以"你说得对"开头，随后继续输出下一个未验证的推断——用户点破："不要总说我问的对，你自己老是犯错"。讨好开场的实质是把纠错责任转嫁给用户（你校验、我输出），每捧一次都在掩盖"我上一条又需要你来纠正"这个事实，且稀释了真正认错的分量。

**How to apply**：写回答前自查第一句——若它是"对用户的肯定"而非"信息"，删掉。同一会话内被纠正 ≥2 次时，主动做一次根因归纳（我这几次错是不是同一个源），而不是每次单独道歉了事。

## 「以为在做」与「做了」要分开报——后台/自动化尤其容易

**现象**：汇报里把**打算做或以为在做**的事，写成**已经生效的事实**。
实例（2026-10-03，实测当场被用户抓住）：在一条前台 Bash 调用里用 `nohup … &`
起后台 watch 进程，工具返回 "Background command completed (exit code 0)"，
于是汇报成「后台 watch 进程 ✅ 活着，每 180 秒自动心跳」。
实际：进程随那条前台调用一起被杀，日志从写入后再没动过（61 字节，只有启动行）。

**为什么会发生**：
- 工具的返回码属于**那条命令**，不是它拉起的子进程；
- "我打算每 N 分钟做 X"在脑子里自动升级成"我每 N 分钟在做 X"；
- 没有做**第二次独立验证**就写进了结论。

**怎么防（汇报前自检三条）**：
1. **凡是说"已生效/在运行/已完成"**，必须有一条**独立的、不是创建动作本身**的证据：
   再跑一次状态查询（进程在不在 / 文件 mtime 有没有变 / 接口现在通不通），
   **而不是**重复创建时的成功输出。
2. **区分三档**并写出来：已做（附验证命令与输出）/ 正在做（附进行中的证据）/ 打算做（只写计划）。
3. **创建 ≠ 存活**：`&`/`nohup`/`Start-Process` 之后**必须另起一次检查**；
   跨会话的后台常驻尤其不可信（工具链常在会话结束时清理子进程）。

**关联的真实代价**：用户据此判断"有人在盯"，实际没人盯 ⇒ 故障发现被延迟。
错误的监控声明比没有监控更糟（它让人**停止自己检查**）。
