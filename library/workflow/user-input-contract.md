## do-not-fill-unprovided-values-with-defaults

**经验**：给用户出配置/报告时，**只写有来源的值**（用户给的、上游文档/接口返回的、本机配置里读到的）。用户没提供的字段（如模型的最大输出、上下文、阈值），一律明确标注「未提供 / 未记录」，不要拿程序默认值去填，也不要替用户选一个。

**Why**：把「程序默认 128K」写成「用户配置的最大输出」是**伪造来源**——用户会以为这是自己设的或上游的，据此做决策就错了。默认值是程序行为，不是用户意图；两者混写后无法分辨。实测：给 dsh-go 写渠道配置时，我把没提供的最大输出按默认 128000 填出，用户直接指出「我没有让你搞最大输出默认 128K，这是不对的，你没有征求我的意见就瞎搞」。

**How to apply**：
- 出配置/汇总时，每个值标来源；无来源的写「未提供」，并说明「需你自己定」。
- 被问「该填多少」时，按 [[ask-and-report]] 给选项+代价，让用户拍板。
- 与 [[ask-and-report]] 同源：不要把「希望/默认」包装成「已定/事实」。

关联 [[ask-and-report]]、[[authorization-and-scope]]、[[model-window-from-upstream-catalog-not-guess]]。

## user-list-to-plan-must-diff-each-item

**教训**：用户圈选的清单是**契约**，不是参考。把它转成计划/任务书/脚本的每一步，都可能无声丢项或改变语义。

### 事故

用户两次明确圈选 ArHub 增补清单（10 项 + 门禁改造）。我转成 dynamic workflow 脚本时只装了 4 项：
漏了审稿分数曲线、DOCX 预览、沙箱恢复；用户拍板的是「恢复」我还做成了「删掉/止血」；另有扩展中心、文件引用、附件徽章缺失。
用户一句「都是我全部要的吗？」点破。

**最危险的形态不是漏项，而是把「恢复」改成了自己的近似词「止血」——方向相反。**

### How to apply

1. 凡从用户清单转出执行物（workflow 脚本 / 任务书 / 批次计划），提交前**逐项 diff**：
   用户清单每项 ↔ 计划中的落点，一行一项；缺项必须补或显式写「本批不含、原因」。
2. 用户对已拍板的动词（恢复/删除/保留/合并）**不得替换**；要改口径先回去问。
3. 交付计划时附覆盖对照表，让用户一眼能核对。
4. 自检问句：「用户原话里点名的每一项，在计划里都能指到具体落点吗？」

## user-given-equalities-must-stay-equal

**经验**：用户用「A=B > C > D=E=F > G」这种写法给你排序时，`=` 是他**明确的并列意图**，`>` 才是先后。
落值必须让每个 `=` 组变成**完全相同的数值**，而且**展示时同档成员只能用并列符号**（`‖` / "并列"），
`>` 与 `→` **只允许出现在跨档**。把同档内的差别（哪怕是真实的抽签比例差别）写成先后关系，
用户读到的就是"你把并列改成了先后"，会直接判定你没看懂他的输入。

**Why**：APIShow「临期优先」组的 priority/weight 设计里，用户给的顺序是
`Loomy=Raccoon > 商汤 > WorkBuddy > CodeArts=Trae=LobsterAI > Astron`。
我把各组落成了 10/9/8/7/6（等号关系其实保住了），但在**尝试链展示**里为了表达"同档按权重抽签谁占优"，
写成了 `Loomy ＞ Raccoon`、`Trae ＞ CodeArts ＞ LobsterAI` —— 用户当场质问
「你没看优先级中我说的有相等的部分吗？权重中我说的也有相等的部分」。
同一轮他还补了两条口径：**不希望出现 0 值**（最低档也要给正数）、以及「小心谨慎」（生产写操作要分步验证）。

**How to apply**：
1. **落值**：先把他给的字符串拆成档位，再一档一个数（档间差 1 即可，别自作主张留奇怪空档）；
   他点名的对象之外若还有别的对象（本例：Qoder / OpenCode / CNB 三个不在榜单里的渠道），
   **照给数值但明说"这是我给的、不在你的榜单里"**，留一个否决口。
2. **自检表**：交付时附一张「你的排序 → 我的数值」对照表，等号组并排写 `10 = 10`，让他一眼验完。
3. **符号纪律**：同档用 `‖`；`→` 只用于跨档；同档内谁分到多少用**比例**说明（"同档按权重抽签 8 : 6"），
   不要写成先后。
4. **生产写**：他说"小心谨慎"就拆成先加后删两步，每步做真请求 e2e + 回读断言 + 备份，
   并在汇报里显式声明**哪些部分没动**（本例：未动 options）。

关联 [[account-pool-friendly-naming]]（同一天的另一条口径纠正：汇报写用户能认的名字而非内部 ID）、
[[plan-before-acting-and-verify-before-claiming]]（先理清再动手 / 声称完成要附证据）

关联 [[sync-semantics]]。

## 单位口径：1K=1000，1M=100万（十进制）

### 经验

面向用户写任何数字（邮件、报告、对话、文档）时，K 与 M 一律按十进制理解与书写：

- `1K = 1,000`，`64K = 64,000`，`128K = 128,000`；
- `1M = 1,000,000`（100 万），`1M context = 100 万 tokens`；
- **不要**把它们当 1024/1048576 系（KiB/MiB）换算，**不要**写「64K（65536）」这种括号注换算——用户看了就是错的；
- 确实想说二进制量（如内存 65536 字节）时，写 `64KiB` 或直接写 `65536` / 「6.5 万」，不用裸 K/M。

### Why

- 用户的单位口径是十进制 SI（tokens、价格、计数语境天然如此），1024 系换算在 LLM/网关语境里几乎总是错的：上游报「128K 上限」就是 128,000 completion tokens，不是 131,072；
- 2026-10-29 实例：给用户的更新邮件里写「最大输出请设 64K（65536）」，站主纠正「以后 1M 是 100 万、1K 是 1000」——括号里的换算画蛇添足且口径错误；
- 混用两种口径会让用户对后续所有数字失去信任（分不清哪个是换算错、哪个是事实错）。

### How to apply

- 逢写 K/M 先默认十进制；数字较大时优先用「万/百万」中文表述（12.8 万、100 万），K/M 只在引用上游原文/配置键名时保留原样；
- 引用上游报错或配置值时**原样照抄**（`max_tokens is too large: 384000`），不自行换算单位；
- 需要精度时写出完整数字（64000 / 1000000），别让读者自己算。
