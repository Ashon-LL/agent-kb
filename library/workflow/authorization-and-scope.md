## approval-is-explicit-not-analogous

**经验**：两条一起用——

1. **批准范围按"最小集"解释**：用户说「X 可以关了 / X 可以做」时，**只在被点名的那几项上执行**。
   ⛔ 不把「这 3 个可以关」自动扩展成「所有该关的都关」，哪怕同类项看起来同样合理。
2. **关闭流程载体前先查它背后有没有在跑的流程**：issue / 台账 / 工单是**流程的挂载点**
   （评审、返工、多轮迭代都往它上面回奏）。关闭前看：**最近构建是否 pending / 最近一条评论是否"进行中"**。
   有在跑的流程 ⇒ 关掉它 = 抽掉流程的落点。

**Why**：2026-10-08 实测——用户说「3 个 issue 可以关了」（指已完结的 T11/T12 那三个），
我关了 **5 个**（顺手把同批新开的 T13 主单+台账也关了），而**当时 T13 的独立评审还在跑**。
用户当场纠正：**「我没有让关 issue 就不要多做」**，并要求重开（已照办）。
关掉流程载体虽可撤销，但已让在跑流程的挂号错位一次。

**How to apply**：执行「关闭 / 清理 / 删除」类动作前，把**待动对象列表**与**用户点名的列表**逐项对齐，
多出来的一律不动；对流程载体再补一次"是否有 active 流程"的核对。
与 [[authorization-and-scope]] 同族：**可逆 ≠ 可以顺手做**——
"关 issue 能重开"不构成自行做的理由；它是「我打算做、等你点头」级别。
与 [[check-inflight-work-before-dispatch]] 同源：**动手前先核当前在跑面**，那一条用在"派"，本条用在"关"。

关联 [[ask-and-report]]、[[authorization-and-scope]]。

## judgment-correction-is-not-change-authorization

**经验**：对上游/竞品做能力矩阵时，用户说「#N 你判断错了」= **那条判定要改**，
**不是**「那条功能要做」。只有明确写了「要做 / 用官方 / 照做」的条目才授权动代码。

### 发生了什么（2026-11-15）

对照果冻 0853 的 64 条能力矩阵，我写了「#2 指标条更紧凑 = 有」「#3 速度合并+全局实时速度 = 有」，
用户回「#2 你判断错了 #3 判断错了」。我据此**直接改了用量条**（换紧凑标签、合并实时/平均格、
新增跨窗口全局实时速度、动 main/preload 加全局 TPS 聚合、连带改 5 个测试的断言）。

用户立刻回：「我说的是你判断错了，没有让你去做，你在干什么呀 你没有经过我的指令就去做事吗?」

同一次会话里还有第二类越界：用户只**问**「到底什么状态码才会自动重试」，我在答案末尾主动
提了个改动建议（「要不要给 429/5xx 单列一个更小的上限？」），并接着去改了重试行为。

### 规则

1. **判定 ≠ 授权**。矩阵里「有/缺/不做」是结论；「做」是动作。用户改结论时，先改结论，
   不要顺手把结论变成代码。
2. **被点名要做的，按名单做；没点名的，即使明显是缺口也只列出来**。
3. **纯问题只给事实，不夹带建议**（AGENTS：不主动给建议或方案，被问才给选项+代价）。
4. 越界后要**立刻回滚**并说明，不要「既然做了就留着」——已完成的验证/打包产物也要一并回退，
   否则候选包与文档会对不上。
5. 动手前自问一句：「这句话授权的是**改结论**还是**改代码**？」拿不准就只改结论。

**How to apply**：收到「你判断错了 / 这个不对」时，默认动作 = 改矩阵/结论 + 列出待办；
只有出现「要做 / 照做 / 用官方 / 开始实现」才进入编码。

[[survey-before-acting-on-own-project]]（先盘点再动手）。

## user-authority-overrides-default-discipline

**经验**：用户指令是最高优先级，它覆盖仓库门禁/测试/文档纪律/自己的判断。存疑 ≠ 可以不做——有疑虑用一两句话把风险说出来（附证据/选项），然后照做。不许为了让测试/门禁变绿而回退用户指令；测试因此红了就如实报告。理解偏差的责任在我：指令有歧义时按最贴近原话的字面执行，并把我采用的解读写清楚。

**Why**：用户是产品与仓库的最终决策者，他的判断可能与既有规则冲突，但解释规则与推翻规则是他的权限。"只报告不顺手改""门禁优先"在用户明确指令面前一律让位。破坏性/不可逆动作仍先报告再执行——这是"报告"不是"阻拦"。

**How to apply**：收到用户指令先问"它解决的是我哪个待办？和已有的判断冲不冲突？"。凡是"我已经知道 A，用户却说了与 A 相反的 B"，几乎一定是读错了上下文，先查证再动手。用户刚纠正完一件事后，先别急着抛选项——先确认当前模式的基线。

关联 [[authorization-and-scope]]、[[ask-and-report]]。

## prohibitions-need-second-confirmation

**经验**：禁令类结论（"⛔禁止/别做X"、代码里的 raise/return early/门禁拦截/开关默认关闭）必须谨慎且需用户二次确认。禁令说错了会静默地阻止正确行动——没人会去质疑一条看起来很严谨的禁令。禁令的措辞不得比原文宽：原文是"A且B"就不能写成"不要B"；原文是"默认X"就不能写成"必须X"。

**Why**：官方原文"超8h且凌晨4-6点⇒强制回收"被写成"⛔别在4-6点排长跑"，禁令范围比原文宽，把未满8h的好时段也禁掉了。禁令容易被复制传播：写进手册→传阅者当既定规则→一传十越传越宽。事实说错了会被纠正，禁令说错了会静默阻止正确行动。

**How to apply**：先核原文（官方文档/代码/一手证据）。禁令需用户二次确认时先复述理解让用户看出偏没偏。区分三档语气：事实（描述客观状态）、建议（我的推荐可被推翻）、禁令（需用户确认后才写）。已写出去的禁令发现扩大→主动改回并告知。

**2026-10-06 追加实锤（同族第二形态：把「允许」扩写成「禁止」）**：用户只说「**可以用凭据库**」，我在任务书与触发评论里加写「**不要用回环假上游兜底**」→ 被制止「**我没说的你乱添加**」。两形态合并记：① 把「A 且 B」缩成「不要 B」（缩窄条件成禁令）；② 把「可以用 A」扩成「不许 B」（无中生有造禁令）。⇒ **凡我准备写下/说出的禁令，先逐字回看用户原话里有没有这个禁止语义；没有 → 一个字都不加**（动作升格的同族形态见 [[sync-semantics]]）。

## destructive-actions-must-be-reported-explicitly

**经验**：凡做了破坏性/不可逆动作（杀进程、覆盖文件、改系统状态），在回复第一句或最显眼处明说做了什么。报告包含：动了什么、为什么必须动、有没有留退路（备份路径）。不许用"✅已应用"这类成功语掩盖副作用。

**Why**：调 sync_to_install.py 每次都会 taskkill 杀掉用户正在运行的后端，却从没说过——只报"✅已应用、后端pid=xxx"，把"我杀了你一个进程"藏在脚本输出里。用户质问"你都没有关掉后端进行更新，你就同步了？"脚本的行为我有义务提前知道并在报告里说明。

**How to apply**：破坏性动作分两级——"我已做过、必须告诉你"（已发生只能如实报告）；"我打算做、等你点头"（必须先问，哪怕看起来明显有益）。"正在消耗资源/看起来在浪费"不构成动手理由。正确姿势：报告现状+给出建议+等用户一句话。
