**经验**：改完补丁后，若「修到完善」的验收必须依赖**用户自己安装到真实环境 + 运行一段时间**
（如内存曲线、调用量、崩溃率），那么构建通过、回归全绿、静态核验、离线自测、沙箱升级/回退实跑、
产物可复现、格式门禁——**全部只是代理信号**，不能替代真实装机后的日志。
正确做法是：把验收写成可一键执行的只读脚本，把阻塞状态和门槛写进项目待办，
然后**停下来等用户动作**，而不是每一轮继续堆新的静态检查。

**Why**：真案例——ZCode 二次改造版修渲染层堆膨胀（JS 堆 51→1745 MB），
补丁、38 条行为测试、26 套回归、守卫门禁、三方源码对照、ADR/KB、两层验收脚本及
离线三场景自测、沙箱升级/回退实跑、7z 逐文件一致、构建可复现全都做完并全绿。
但装机 asar 一直是旧哈希，验收脚本如实返回「未安装本修复，运行态验收不成立」。
期间反复做完成度审计、加工具、补文档、改脚本自测——**没有一条能推进目标**，
反而把静态证据越堆越多，看起来像在推进，实际是原地打转（用户要的是真实运行态结论）。

**How to apply**：
1. **先分清证据类型**：静态（构建/测试/门禁）、隔离（沙箱/离线自测）、运行态（真实环境日志）。
   目标写的是运行态，就只认第三类；前两类只用于排除「工具本身会崩」。
2. **把验收工具做完就停**：一键脚本要能自证「未安装 → 明确失败、数据不足 → 明确说还差多久、
   好数据 → PASS、坏数据 → FAIL」。做完这些后继续加检查没有收益。
3. **阻塞要显式留档**：在项目 `open-items` 写清「当前阻塞=用户尚未安装/未授权代跑」、
   需要哪个动作、一键验收命令、四项指标门槛、「不达标继续定位不标完成」。
4. **需要授权的动作绝不擅自代做**：写生产目录 / `Program Files`、重启用户应用、
   发版、删除——按权限规则等用户明确确认；不要用「我帮你跑一下」绕过。
5. **给用户最小动作**：一个可点链接 + 一句「回『已安装』或『授权代跑』」，
   不要每轮重复长篇状态汇报。
6. **拆验收层级**：能即时判的特征（如某接口调用量突然连发）单独做即时脚本，
   需要长时段的指标（堆地板斜率、峰值）留在 ≥4h 脚本；即时 PASS 明确标注「不构成完善结论」。
