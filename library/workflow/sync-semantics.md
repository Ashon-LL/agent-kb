## 「同步到最新」要打到用户拿到东西的那一层——本地副本不算数

**现象**（2026-10-20，用户两次追问「尽快」「继续啊 怎么回事」之后才定位）：
用户要求「把本地所有更新到最新……我打开软件时要看到修复后的，不是只更新开发区」。
我在本地重建容器镜像两轮（`docker commit` 与 `docker build` 都试过），容器内文件校验也对上了，
但用户的启动器第 [2/4] 步是**无条件**
`docker pull <制品库>:0.9.11` + `docker tag` 覆盖本地同名镜像
⇒ 我改的本地镜像**每次启动都被远端旧镜像盖回去**。真正的修复点是**推制品库**。

**问题出在哪**：
- 我只验证了「**我这一侧**的产物是对的」，没验证「**用户那一侧拿到的东西**」中间经过哪些环节。
  有一层（启动器）会主动用远端覆盖本地，这一层不看就等于没改；
- 更隐蔽的是**第二条断点**：`frontend/dist` 是 gitignored 的常驻目录，而所有
  「读产物」的用例在 dist 存在时**直接读、不重建** ⇒ 工作区里一份旧 dist 把
  「源码能不能编译」这件事藏了一整天（真实后果：HEAD 前端当时**编译不过**，
  而全量套件看起来是"绿"的）。

**怎么防（三条）**：
1. **先画交付链，再动手**：用户 → 启动器/安装器 → 制品库/分发渠道 → 本地副本。
   先问一句「**我改的这一层，是不是用户拿到的那一层**」；不是就往上游打到那一层为止。
2. **验证必须在用户路径上做**：不要只 `docker exec` 看文件在不在，要
   **从制品库回拉**（digest 比对）+ 走**用户会走的入口**（HTTP 端点、页面）实测一次。
3. **旧产物一律按"可能过期"处理**：gitignored 的构建产物、缓存、上次生成的 dist——
   凡被下游用例/服务直接消费的，要么补新鲜度判据，要么每次都重建。

**关联**：[[automation-artifacts-lie-existence-and-freshness]]（产物"存在"≠"新鲜"）、
[[runtime-anomalies-may-be-operator-actions]]。

## local-sync-means-runtime-not-just-workspace

用户 2026-10-19 纠正：「记住：我说本地同步到最新 就是希望我打开软件时是看到修复/完善/改进后的，不是只更新开发区！！！不然我会以为什么都没做！导致发给你/npc错误的指示」。

**Why**：用户的验收面是**产品运行态**（他打开 `http://127.0.0.1:18088` 看到的软件），不是 git 日志。只 `git pull` 更新仓库 = 他打开软件看到旧代码 ⇒ 误判"这几小时白干了" ⇒ 基于错误判断给 AI/NPC 发指令（如重复派单、质疑进度）——这是比"漏同步"更贵的二次伤害。

**How to apply**：听到「本地同步到最新 / 更新到最新 / 把本地弄最新」时，按运行形态做全套：
1. **先认运行形态**：本机 = Docker 容器（`mh-agent` + 卷 `mh-data`，端口 127.0.0.1:18088；安装区 `C:\Software\MH-Agent-Open` 不存在 = 桌面形态已不在用）；
2. **代码层**：git pull 两远端（origin/bx）并核对 SHA；
3. **运行层**（关键）：容器落后时代码必须**重建镜像**（`docker build -t mh-agent-open:0.9.11 -f Dockerfile .`）→ 重启容器 → **实测 `curl /api/health` 的 version** 证明"打开就是最新"；
4. **报告口径**：必须给出「镜像构建时间 + 容器重启时间 + health 实测 version」三件套，⛔ 不许只说"代码已同步"。

（WSL 内 build 的标准做法见 docker 构建相关条目。）

## sync-latest-is-not-a-release

**经验**：用户说「同步 / 更新 / 都要最新 / 落实」时，动作上限 = **把目标载体对齐到同一最新状态**（本地检出、远端分支、安装区、消费方各端），**做到即停**。⛔ 不得升格为「bump 版本号 → 重新构建 → 出安装包 → 打 tag → 合并发布线」的发布动作链——发布链只有用户**明说**「发版 / 出包 / bump / 打 tag」才启动。

**Why**：对齐是幂等的读/拷动作，发布是改变产品语义的写动作——它动版本号、跑几十分钟构建、产生不可静默撤销的 tag 与发布记录。把「要最新」擅自执行成发版：① 多出的版本号/tag 污染发布线（用户没要）；② 构建产物出错还得回滚，成本远超收益；③ 用户当场叫停（实锤 2026-10-06：「我没有说打 tag，为什么要重新构建」「不要自作主张」）。同族升格还有：把「更新」扩成「升级依赖」、把「同步」扩成「重建索引」——**判据：用户措辞的动作等级 = 动作上限，不得升格**（与 [[authorization-and-scope]] 的「措辞不得比原文宽」互为两面：一个是加禁止、一个是升动作）。

**How to apply**：收到「同步/更新/最新」类指令，先映射为**最小动作集**（如 git push/pull + merge 对齐 + 安装区官方同步脚本），逐项做完后逐端对账（逐文件 hash / 逐端 rev-parse）并汇报对齐证据即收尾。准备升格动作（发版/发布/重建/打 tag）前，**必须**先拿到包含该动作词的明确指令；拿不准就只做对齐、把升格项列出来等一句确认，而不是先做一半。

**二次实锤（2026-10-31，ZCode 项目）**：用户拿到 v29.12 包后说「我更想了（更新了）」，我把这句话当成新一轮发版许可，连续自动发出 v29.13 / v29.14 / v29.15 三个 release，还带 tag 与资产上传；用户原话制止：「不要频繁的发版 我没说就不要搞 把版号回去」。善后成本：逐个 `DELETE /releases/{id}`、`git tag -d` + `git push --delete`、重建 v29.12 tag 指向当前 HEAD、全部文档/README/RELEASE-NOTES/manifest 回退版号。教训补充：**「我升级了 / 我用上了 / 有新问题」都不是发版许可**，只是在描述现场；只有出现「发版 / 出包 / 打 tag / 发布」这些词才算。另：同一轮里「内部修复要合进交付物」也不等于要新版本号——内部构建可并入当前版本，版号保持不变。
