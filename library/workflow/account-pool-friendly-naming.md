# 账号池/渠道汇报：用「用户可认的称呼」而非内部 ID

**经验：** 涉及「账号池 / 多来源凭证 / 供给渠道」的汇报，一律用用户自己起的称呼——手机尾号（尾号4600）、系列+序号（接码#2/#3）、来源（实卡号1、国际版）、**渠道源名（WorkBuddy / 商汤 / Loomy …）**——**禁止裸内部 ID（uuid 前缀/8 位十六进制）、裸序号与内部渠道号（ch176 之类）**。内部 ID 用户认不出，裸序号在来源多批并存时必然撞车。

**Why:** APIShow WorkBuddy 池（尾号/接码/实卡/国际版 四来源并存）被用户连续纠正两次：
- 2026-09-27：「3号」在接码系列（接码#3）与尾号系列（a9034352 历史被叫过三号）之间撞车；
- 2026-09-28：「不要说 UID，要说我们对它的称呼。尾号系列用【尾号+手机尾号+(昵称)】，接码系列用【接码+#+序号】」——我的内部 ID 汇报用户一眼认不出是谁。
- 2026-10-17（**同一坑的第三次**，从账号蔓延到渠道）：「我说了不要跟我说渠道号，我看不出来他是哪个渠道。你直接跟我显示它是什么渠道。」——我在优先级/权重表里写 `ch176=5/ch29=4`，用户完全无法对应到源。

**How to apply:**
1. 新接入账号**立即登记**「称呼 ↔ 内部 ID ↔ 手机号」映射表（称呼在前，内部 ID 只做锚点），防止后续汇报退化回 ID。
2. 汇报/答复一律用称呼；内部 ID 只在命令、脚本、DB 查询里使用。
3. 系列命名遵循用户既有约定（尾号+手机尾4位、接码#N、渠道取源名），**不要自己发明序号或缩写**；新增账号的序号先与用户确认。
4. **渠道/供给线的显示名 = 站点渠道名里第一对【】的内容**（`【WorkBuddy】【9模型】【ch176】` → `WorkBuddy`；无括号的按其源名短称）。写个清洗函数（APIShow 是 `clean_channel_name()`）并在所有报告里复用，别每次手写。
5. **自检**：交付前搜一遍正文有没有 `ch\d+` / uuid / 裸序号；命令、SQL、脚本里可以留，用户可见的文字里一律不出现。
4. 台账双标（称呼 + 内部 ID 前缀）便于对账与排障。
