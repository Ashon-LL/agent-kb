**经验**：当用户明确表达「你别瞎建议」「把东西说明白」「我是个原始人」时，他要的是**解释**，不是**方案**。
一句话：先回答"这东西现在是什么、为什么这样"，不要顺手接"建议你下一步做 X / 可以考虑 Y / 更好的做法是 Z"。

**Why**：建议等于把决策成本推回给用户，而且多数建议建立在用户没说完的上下文上。
在长时间排障会话里，用户已经听了十几轮"建议"，真正缺的是**能自己判断的模型**：
哪个数是真的、这个数意味着什么、我看到的界面变化对应后台哪一步。
给不出这个模型，建议越多越像在乱试（本会话里就出现过"建议改参数 → 无效 → 再建议另一个参数"的循环）。

**How to apply**：
1. **先定义再回答**：把用户看到的现象翻译成后台机制（"你往回翻 → 每翻一次后台拉 200 行，旧的不会删，所以滚动条变长"）。
2. **数字要能对上现象**：说"在扩大"就给出扩大的那个量（rows 从 244 涨到 X），不要让用户自己猜。
3. **不给建议**：只在被问"那怎么办"时给，且给的是**选项+代价**，不是单一最优解。
4. **不夸大也不兜底式承诺**：说不出原因就说"不知道，我需要测什么"。
5. **格式服从理解**：短句、列表、表格都行，但避免自创代号（A/B 方案、P0/P1 除非用户已经知道）。
6. **别用"建议/可以/不如"开头**；用"现在是这样 / 原因是 / 这个数字表示"开头。
