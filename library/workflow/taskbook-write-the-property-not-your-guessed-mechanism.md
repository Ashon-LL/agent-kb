**经验**：派单任务书里，**区分「目标/性质」与「手段/写法」**。
写死手段会把执行方逼进两难：**要么违反你的字面要求，要么破坏正确实现。**

## 真实案例

**背景**：我要给 openclaw 调用加硬超时。任务书里写了：

> **B1**：`agent --local` 调用加**硬性** `--timeout`（不再依赖 `step.timeout > 0` 才拼）

并给了目标写法：

```python
# 改成（目标写法）—— 无论 step.timeout 是否为 0，都要拼
effective = step.timeout if step.timeout and step.timeout > 0 else DEFAULT_OPENCLAW_TIMEOUT_S
args += ["--timeout", str(effective)]    # DEFAULT = 600
```

**执行方的实测回报**：本仓现状是「未设则不拼」，而 openclaw 的
`--timeout` **内置默认就是 600**。⇒

| 方案 | argv | 效果 |
|---|---|---|
| 现状（不拼） | 无 `--timeout` | 上游用自己的 600s |
| 我的 B1（拼 600） | `--timeout 600` | 显式下发 600s |

**数值完全等价。** 而执行 B1 的代价是**推翻一条有实测依据的既有断言**
（`tests/test_ignored...:171` 断言「未设则不拼」，注释写明理由：
传 `0` 在该 CLI 语义里是**禁用超时**，与「用默认 600」是**完全相反的行为**）。

⇒ **我的目标（让调用有界）是对的；我写的手段（在 argv 上拼默认值）
在本仓恰好已被等效实现，收益为零、代价是破坏一条正确断言。**

## 正确写法

⛔ **不要写**：
> 把 `if step.timeout > 0: args += [...]` 改成总拼 600

✅ **要写**：
> **要守的性质**：任何一次外部调用都必须有**有限**的时长上限，
> 且**绝不下发**表示「禁用超时」的值（如 `--timeout 0`）。
> **手段不限**：若现有实现已满足该性质（例如上游自身有确定性默认值），
> **请回报说明并保持现状**，不要为了字面一致去改动它。
> ⚠️ 若为满足字面要求而需要改动 `tests/` 下既有断言，**先停下回报**。

## 双向义务（派单方 + 执行方都要记住）

**派单方（我）**：
1. 写 B 类改动时，先问一句「**我要守的到底是什么性质？**」
2. 把「手段」标成**建议**而非**要求**。
3. **显式授权**执行方在「既有实现已满足性质」时**回报而非硬改**。
4. 保留一条「与仓库实际不符就停下回报」的硬约束（本次救了场）。

**执行方（NPC）**：
1. 发现任务书前提与仓库实际不符 ⇒ **先停下回报**，附**可复算证据**（文件:行号）。
2. ⛔ **不得**为了满足字面要求去推翻有实测依据的既有断言。
3. 若确有更准的做法，**给出理由 + 选项 + 建议**，交派单方裁定（本次 NPC 做到了：
   列出方案 (a)/(b)、说明为何推荐 (a)、并声明「未收到裁定前不合并也不改测试」）。

## 一个信号：执行方回报「任务书前提不成立」时，那通常是真发现

本次 NPC 顺带指出我另一条前提也错了：

> 任务书 §2.3 说「若仓库已有等价机制（`subprocess` 的 `timeout=` + `kill()`），优先复用」。
> **搜下来不存在该等价机制**（grep 命中的 `Popen` 只有一处，且**没有** `timeout=`）。

⇒ **别把这种回报当成「执行方在找借口不干活」**。逐条复核后若属实，
**任务书要改、裁定要发，并把这条教训记住**。
