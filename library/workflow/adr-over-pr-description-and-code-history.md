**经验**：一个决定「为什么这么做」的理由，按这个优先级落：**① ADR / 设计文档（首选，独立成篇、带日期与背景）→ ② 代码注释（次选，只留「违反即踩坑」的约束与指向 ADR 的链接）→ ③ PR 描述（仅作当时的工作说明，不作为决策的长期载体）**。三者不是替代关系：PR 描述负责「这次改了什么」，ADR 负责「为什么只能这样」，代码注释负责「改这块时别踩什么」。

**Why**：PR 描述的读者是「当时的评审者」，它天然带上下文（链接、讨论、当时的代码状态），随时间推移这些上下文会失效——链接失效、代码已变、讨论散落在平台里，半年后读到的人只有结论没有依据。反过来，把长篇史书写进代码注释会让代码变成编年史，注释与代码一起被复制、被格式化、被误改，且无人维护。ADR 独立成篇则既有上下文又不污染代码：代码注释写一句「原因见 ADR-xxx」即可。

**How to apply**：写任何非显然的取舍时（为什么删掉某个配置、为什么选这个镜像、为什么门禁改成不阻断），先问「半年后的人凭什么理解这个决定」——凭 PR 描述不够，就补 ADR；代码里只留「不许怎样 + 指向 ADR」。评审/交接时，**不要引用 PR 描述当依据**，去读 ADR 或代码注释。
