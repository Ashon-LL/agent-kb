**经验**（比"试到好为止"可靠得多的排查法）：

1. **根因分层排除**：先列出全部可能原因，逐条做实验排除并记数据，直到锁定真因。
   实例：标题缩进三层——① 段落级 `w:ind` 与 `numbering.xml` 叠加 → ② 删掉后继承样式链 → ③ **真凶是继承来的 `firstLineChars` 优先于数值型 `hanging`**。
2. **对照实验留证**：每个假设做最小复现，把实测数字写进记录（"iters=1/2/3/5 的表面增量"、"五种缩进写法的序号/续行坐标"）。**没有数据的根因判断不算结论。**
   **⚠️ 但对照组必须包含「基线身份 / 空凭据」这一档，否则结论会反向**（2026-09-21 实锤）：查某凭据"有没有权限"时，我只看「用该凭据请求 → 200」就判定"有权限"，**这是错的**——那 5 个目标里有两个是**公开资源，不带任何凭据也返 200**。补上三档对照才分辨出来：<br>
   `有凭据=200 / 无效凭据=404 / 无凭据=401` ⇒ 该凭据**确有**权限；<br>
   `有凭据=200 / 无凭据=200` ⇒ **资源公开，与凭据无关**（此档结论完全不成立）。<br>
   推广：任何"某身份/某配置/某开关是否产生影响"的判断，对照组都要含**去掉它**的那一档；只测"有它时成功"永远无法区分"是它起作用"还是"本来就成功"。
3. **换向验证**：修好后做一次反向检查，确认修复没引入新问题（如改字号后复验"图片未被裁、公式仍居中"）。同样适用于**改动的影响面**：改配置后要验证**未被改动的对象仍保持原值**（本例改 A 库凭据后，逐库复测其余 4 库凭据指纹未变）。
4. **区分"缺陷"与"字形错觉"**：曾把 en dash（U+2013）的宽字形误判成"两边有空格"。**涉及字符的判定必须查字节/码位，不要凭渲染图下结论。**
5. **修复脚本必须限定作用域**：批量替换（如参考文献重编号 `[n]`）必须排除附录源码代码块——本项就因未排除把代码里的 `ax[1]` 改成了 `ax[3]`，直接触发"程序与论文不符"红线。改完必须校验被改文件与磁盘源码逐字节一致。
6. **⛔ 别把"权限不足"当"对象不存在"**（2026-09-21）：私有资源在鉴权失败时，**报错文案常常是"不存在"而不是"无权限"**——本例 git 推私有库失败报 `Repository Not Found`，我一度去查"仓库是不是被删/改名了"，而真相是凭据用错了。**看到"不存在"先验一遍"凭据对不对"，再怀疑对象消失。**
7. ⭐ **别把"我能想到的机制"当根因，先问用户/先做反证**（2026-09-28 实锤，被用户当场纠正）：看见窗口启动后是最小化的，我立刻归因成"Windows 继承了父进程 `STARTUPINFO` 的 show 状态"，并把这条**推断写进了代码注释和守卫文档**当作事实；用户一句"不是被启动方式弄成最小的，而是我手动了"直接推翻。⛔ 这条与第 2 条同源：**归因需要对照档，而"用户自己干的"这一档是我列不出来的**——凡现象可能由用户操作产生（最小化/关窗/改设置/拖走文件），先**问一句**再下结论。<br>
   ⇒ 正确的处理：把推断**降级**回注释里（标【推断，未取证】）、把代码改成**兜底语义**（显示路径先 `unminimize` 再 show——这条本来就该做，与成因无关），真问题另找（那次真正被抓出来的是"最小化时 `GetWindowRect` 返回 `(-32000,-32000)` 哨兵，被当成几何存了"）。

**Why**：同类教训是"**修复动作本身也会引入缺陷**"——凡是批量改文本的操作，改完都要重跑一致性校验 + 逐页目视验收。

**How to apply**：遇到"改一次冒一个新问题"的排查（排版、编码、坐标对齐），先停止试错、按 1→5 写一份带数字的排查记录；批量改动前先圈定"哪些区域绝对不能动"。**凡是结论形如「X 导致了 Y」，先问自己：没有 X 的时候 Y 会怎样？没测过这一档，结论就不成立。** 再补一句：**「X 导致了 Y」里的 X 若来自我的脑补而非实测，先找当事人确认一遍再写进文档。**
