## subagent-orchestration-lessons

**经验**：

- **可并行**：各子代理持有互不相交的文件集 + 主线先冻结精确 API 契约 + 各自跑构建验证再交付。**不并行**：共享同一视觉语言/同一文件的创作型任务（先主线冻结设计令牌再摊发）。
- **大批量改造前**先给校验器/状态机等纯逻辑补单测，回归会被首跑抓住。
- **子代理半途失败**：成果在上下文里、剩余工作明确 → `SendMessage(原 agentId)` 续跑（点名"不要重做已完成部分"）；重派=上下文全丢；误派立即 TaskStop。
- **禁长 sleep 阻塞**：run_in_background 起轮询脚本，等待期并行做独立工作；区分常驻服务与一次性监控，后台"运行中"≠卡死。
- **并发有上游限流**：批量重跑会触发网关全面限流连锁失败；首跑可并行、重跑小并发串行 + 队列水位控制。
- **验证类任务 prompt 要自包含**（API 用法、异常处置、"遇 paused 先 resume 再判断"、禁改代码只报告）；等确认"真在跑且有输出"再放开下一批。

关联 [[semantic-unit-vs-execution-unit-must-be-separate]]。

## check-inflight-work-before-dispatch

**经验**：发起「派单 / 开 issue / 写任务书」之前，先跑**三查**确认没人正在做同一件事：

```bash
cnb pulls list-pulls --repo <owner>/<repo> --state all   # ① 开放 PR 里有没有同题
git ls-remote --heads origin                             # ② 远端分支里有没有同题
cnb build get-build-logs --repo <owner>/<repo> --page-size 8  # ③ 最近构建标题里有没有同题
```

三查任一命中 ⇒ **不要派**；改为「给在跑的那支补充信息 / 收窄它的范围」。

**Why**：2026-10-08 实测——派单方基于「自己记的 follow-up 待办」派了 T14（工具面计数 35→37 订正），
而执行方（NPC）**早已开 PR #164 在做同一件事**，且已过评审。结果两支都做了同一段改动：
派单方须收窄 T14 范围、force-update 分支、补发范围说明评论，纯属重复劳动 + 制造合并面。
根因：只核对了「我记的待办」（历史面），没核对「别人正在做什么」（当前面）。

**How to apply**：任何派单动作前跑三查，**和"读自己台账"同等重要**。发现重叠时的优先级：
① 让在跑的那支继续（它的上下文最全）；② 把新发现**收窄成差集**补给在跑的那支；
③ ⛔ 不要停掉在跑的重派（丢上下文、白烧已完成的量）。
与 [[backlog-records-rot-verify-before-dispatch]] 互补——**那条查「历史是否已做」（记录会腐烂），
本条查「当前是否有人在做」（在跑的工作不在你的记录里）**；两条合起来 = 派单前的两个核对面。
与 [[two-agent-iteration-and-deadlock]] 同族：派活板是异步档案，**不实时反映在跑状态** ⇒ 板子之外还要查在跑面。

## 派单前核三方等值 + 载荷先入仓 + 产物落项目内（用户 20261021 连斥三条）

**现象**（用户原话）：
- 「**本地有未上传的为什么不上传再派单？**」
- 「本地已有 7 个未推提交（`20430d84`、`b4aedec1` 及更早 5 个）你知道
  吗？**为什么要搞偏移**！！！！！！！」
- 「一定要放在 `<项目文件夹>`……**不是其他地方，不是 `~/.zcode/workspace/<项目>/`**！！！……
  做好项目卫生，不要到处乱放产物！！！」

**根因（三条，都是我的流程缺口，不是误解）**：

1. **等值核验的时机错了**：我在**自己每次 push 之后**都核过 local/bx/origin 等值 —— 但
   **派单前没有重新核**。而派单意味着**外部执行者开始写同一个仓**：那次派单后 87 秒内
   目标仓就多了 3 个提交（我的任务书成了它们的父提交），本地还另有 1 个未推提交
   ⇒ **三方分叉**（local 有 A，bx 有 B+C+D，origin 停在共同祖先）。
   教训：**「我上次核过」在派单语境里一律无效**；宿主的等值只是**某个时刻的快照**，
   任何外部执行者动作之后就过期。
2. **载荷传递用了旁路**：执行者在容器里**没有平台登录态**，我拿一次性签名 URL 让它 `curl`
   —— 会过期、不可复现、且与"产物必须在项目内"自相矛盾。正解是**先入仓再派单**
   （`docs/dispatch/attachments/`，并写清许可证与清理条件）。
3. **产物散落在项目外**：`ego/`（43 M 暂存包 + 派单 payload）不在项目目录里。
   正解：项目内 `_tmp/`（**先确认 `.gitignore` 有规则**，否则会污染未跟踪列表）。

**怎么防（可复用的四步）**：
1. **派单前三方核**：`git fetch` 两远端 → 比 `local` / `开发主场` / `发布线` 三个 SHA；
   **不等就先统一**（rebase 到主场之上 → 推两仓 → 再核一次），绝不带着分叉派单。
2. **载荷先入仓**：执行者要用的东西（技能包、夹具、素材）**提交进仓**并在任务书里给**仓库内路径**；
   ⛔ 不用签名 URL、不进 `_tmp`（`_tmp` 是 gitignored，执行者读不到）。
3. **产物落点唯一**：`<repo>/_tmp/`（先补 `.gitignore` 规则）。⛔ 不写 `~/.zcode/workspace/`、
   `~/ego/`、`%TEMP%` 或任何项目外目录。
4. **派单后立刻重核**：目标仓会被执行者推进 ⇒ 第一时间再比三方，发现分叉就地统一
   （并保留 `backup/pre-unify-<date>` tag 作退路）。

**关联**：[[sync-semantics]]（同一族：只核自己这一层不够）。

## shared-guide-for-parallel-agents

**经验**：当同一个系统（服务器/站点/仓库）会由**多个入口**操作——比如一个人手上的电脑 agent 和手机 agent、或多人多会话——最省事故的做法是维护**一份共享指南**，而不是让各方各自揣着记忆和本地配置。

- **只写当前正确口径**：指南里只写「现在是什么、该怎么做」，历史错误一律不进正文，最多以「⛔ 不要这样」列一行。写错误细节会误导后来者，也会把已被推翻的旧结论固化。
- **指明唯一事实源**：如「渠道/分组/ratio 以线上 X 为准」「代码以仓库 Y 的 main 为准」，避免各方用本地旧值覆盖生产。
- **动生产前先读实时状态**：另一方可能刚改过/重启过；任何变更前先只读核实（GET/状态查询），再动手。
- **改动留痕**：备份 + 脚本 + 提交，让另一方回看与回滚有据。
- **红线集中列**：把「绝对不要动的东西」单独成节，比散落在各条规则里更不容易被违反。

**Why**：2026-11-10 实测——站主同时在电脑（ZCode）和手机（dsh，经 `dsh web` 连服务器）操作同一台服务器/同一个站。若两边各自按自己的记忆改配置，极易出现「一边刚改完、另一边用旧值覆盖」的静默冲突；且手机 agent 扫过全机但对站点业务理解不全，容易做出偏离正确口径的动作。

**How to apply**：
1. 检测到「多入口/多 agent 共管同一系统」时，先建/更新那份共享指南，再派活；
2. 指南放在各方都容易拿到的位置（如服务器 workspace 根目录 + 仓库各一份）；
3. 每次系统状态有变（源上下线、配置口径变、红线变），同步更新指南；
4. 任务结束时检查指南是否仍与实时状态一致，不一致就修。
