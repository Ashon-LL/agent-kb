**经验**：最小改动是排序规则不是不修缺陷；边缘功能不主动开战线；修完闭环即止

> 本条由 3 条同族条目合并；原文判据、反例与实测命令保留在下面各节。

## minimal-change-and-no-scope-creep

**经验**（用户三条铁律，同族合并）：

1. **字面最小改动**：说"把 X 改为 Y"就是改 X 为 Y，勿扩大解释成重构；术语/概念讨论≠改动指令；推断出更大需求先问。改完 diff 里出现指令未提及的文件/结构调整 = 危险信号，自查回滚。
2. **能运行就别乱动**：修复闭环（测试+部署+E2E 通过）即停；发现的额外问题只记录进报告供用户决策，不动手；未请求的改动=未授权风险。计划/授权里写了"不提交/不推送"就是硬约束，技术理由再顺（如"门禁只认 HEAD 树"）也不构成覆盖——想破例先申请。0915 案例：验收任务途中见发布门禁 FAIL，自行占位符化 CI 配置注释并提交，被用户两次点名后回滚；该"修复"本身还是错的（真实 URL 是功能文档）。
3. **不做表面修补**：不为测试变绿删测试/绕根因/monkeypatch 掩盖；每次改动定位根因，并从正确性/可维护性/一致性自查。

**Why**：0904 两次扩大解释被批、整批改动连已推送 master 作废强推回退；"顺手改进"是多起返工的根源。

**How to apply**：动手前先在心里圈定字面范围；涉及 UI/术语/信息层级的改动，先把改动清单逐条列给用户确认再开工。

## 最小面原则会退化成「发现了但不修」

**现象**：Agent（或你自己）排查出真缺陷后，因为「保持改动面最小 / 不扩大范围」而
只报不改、或改一半留个 TODO，缺陷就烂在那里。实测：`comp-code` 这个问题拖了 3 天 4 轮
（每轮都"发现"了，每轮都"先不动"）。

**为什么会发生**：最小面原则本来是**排序规则**（同样要改时先改影响小的），
但很容易被当成**筛选规则**（有别的更要紧的就先放着）。而"别的更要紧的"永远排队，
于是"次要"的永远不动。

**代价**（实测过的两种，都很贵）：
- 留在代码里 ⇒ 下一个维护者重新发现一遍；交接文档里变成"已知遗留"。
- 变成隐性地否决：明明已经证明是真问题，却因为"这轮不碰它"而被当成不重要。

**做法**：
1. **排序用最小面，筛选不用**。要不要修，看「真不真」（有没有一手证据），
   不看「这轮方不方便」。有证据的真缺陷 = 本轮就修。
2. **"范围外"要写进交接，而不是留在代码里**。真要留，写清「已定因 + 为什么这轮不做
   + 什么条件下做」，并进 `docs/dispatch/` 或 INBOX 派活板（能被下一个人捡起）。
3. **复算时看到红就问"这条是真缺陷还是用例自己的问题"**，别用「测试有问题所以不算」
   一句话糊过去。本仓就有过两例：用例硬编码 POSIX 路径在 Windows 上必红（该修用例）、
   用例写死字节数在多字节文本上假红（该修用例）——但也有"测试抓到了真缺陷"（该修产品码）。
   **两种都要处理，只是修的地方不同。**
4. **把「先不动」写成待办交出去**，而不是记在脑子里。派活板（`docs/dispatch/INBOX.md`）
   就是干这个的。

**一句话**：*最小面是"先修哪个"的规则，不是"能不能不修"的许可。*

## dont-open-frontline-for-edge-features

**经验**：改一个"本来没坏、只是不通"的东西之前，先问：它挡住主线了吗？不挡就降级，别修。降级路径已经存在且干净时（写明原因、留占位、不伪造），那是完成态，不是待办。

**Why**：为截图能力开贯穿四层管线（Dockerfile→setup 脚本→守卫用例→白名单），40 分钟净零产出后全 revert。它从来没挡住主线——技能侧降级本来就很干净。修"不通"的默认代价参照物是主线，不是"我能不能修好"。

**How to apply**：给边缘功能动 Dockerfile/密钥库/全局白名单之前先自问这条管线有几层。一层（运行期幂等脚本）可以接受；四层不值。执行方抗命改判据时先复算——别把自己的推断当规格。
