## 一、硬约束（破坏这些 = 任务失败，不论其他项做得多好）

### C1. `INDEX.md` 的路径与条目行形状是外部契约

`hooks/kb_core.py` 在读它：

| 事实 | 位置 | 含义 |
|---|---|---|
| `INDEX_FILENAME = "INDEX.md"` | `kb_core.py:27` | 文件名不能改，也不能移走 |
| `_INDEX_ENTRY_RE = ^\s*[-*]\s+\[[^\]]*\]\([^)]+\)` | `kb_core.py:30` | **只有匹配这个正则的行会被计数**，其余行一律不算 |
| `count = count_index_entries(resolved)` | `kb_core.py:106` | 统计结果被拼进**每个会话**的注入文本 |
| 注入文本形如「全局经验库 … 就绪（INDEX.md 收录 N 条）」 | `kb_core.py:108` | N 是每会话可见的事实，必须为真 |

⚠️ **最危险的失败模式是静默的**：`count_index_entries` 内部 `try/except` 吞掉一切异常并返回 0，钩子本身 fail-open、绝不阻塞会话。也就是说——**你要是把条目行改成了不匹配上述正则的形状，钩子不会报错，它会安静地告诉所有会话「尚无条目」。** 改 INDEX 前后都必须实测这个函数。

**验收方式**（必须实跑，不接受「应该没问题」）：

```bash
AGENT_KB_PATH="$PWD/library" python3 -c "
import sys; sys.path.insert(0, 'hooks')
from kb_core import count_index_entries, session_start_reminder
print(count_index_entries())      # 期望 110，与磁盘 .md 条目数一致
print(session_start_reminder())   # 期望注入文本里的 N 与上面相同，且不为 0
"
```

> 基线（搬入 `library/` 时实测，供你复算）：`count_index_entries() = 110`，注入文本为「…就绪（INDEX.md 收录 110 条）」。

### C2. 条目 schema 是注入给用户的规程，不能与实际不符

`user_prompt_reminder()`（`kb_core.py:122`）向会话注入：「按 kb 技能规程落盘（frontmatter: name/description/type/source/date；正文: 经验/Why/How to apply）」。

**⇒ 你若改动 schema（新增字段、改必填项、改正文三段结构），必须同步更新这段注入文本**，否则用户和 agent 会收到错误规程。

⚠️ 该注入文本位于 `hooks/kb_core.py`，属于第四节第 2 条「要停下回报」的情形：改 schema 时请**同时给出注入文本的改法**，一并等裁定，不要擅自改钩子。

### C3. 知识内容不得丢失

- 库已在 git 里（`library/`），**有版本历史兜底**。动手前先确认工作区干净；需要大改时开分支。（本条相对原版已更新——原任务书写于库还在本机、无版本控制时，现已具备。）
- 任何「重写 / 合并 / 精简条目」的动作，**不得删掉已有结论、证据、量化数据**。要合并就合并进保留最全的那条，并把另一条的独有内容并进去。
- 索引行与磁盘文件必须一一对应（当前 **110:110**）。

## 二、阶段 1（P0｜每会话都在付费，且不碰知识内容）

### 现状基线（实测于 `library/`，供你复算）

| 指标 | 现状 |
|---|---|
| `INDEX.md` 总行 | **190**（索引行 110 + 沉淀记录 42 + 其他 38） |
| `INDEX.md` 字符数 | **46,514** |
| 索引行字符数 | **37,788**（平均 **344** / 最长 **1599**） |
| 沉淀记录字符数 | **8,118** |
| 每会话粗估 token | 索引行 ≈27,000 + 沉淀记录 ≈5,800 = **≈32,800** |

> 复算口径：字符数按 UTF-8 解码后的 Python `len()`（LF 行尾，含全部字符）。索引行按 C1 的 `_INDEX_ENTRY_RE` 计数；沉淀记录指以 `>` 开头的行。

### P0-1｜变更日志必须离开检索面

**要守的性质**：每会话注入 + 用户主动读 `INDEX.md` 的成本，应与「判断某条是否相关」所需的信息量成正比；**纯历史记录类内容不得出现在 `INDEX.md` 里**。

- 依据：那 42 行 `> 2026-09-XX …` 沉淀记录对检索**零贡献**（没有一条是条目、没有链接），却占 5,800 token/会话，且只会单调增长。
- 手段建议：移到 `library/CHANGELOG.md`（或你判断更合适的位置）。**手段不限。**
- 硬约束：搬走的是**格式与位置**，内容不得删减。搬完 `INDEX.md` 里的 `- [标题](路径)` 行数必须仍为 110。
- ⚠️ 那些记录里含有**有价值的沉淀线索**（哪条什么时候因为什么被修订、用户纠正了什么）。建议保留全文，不要为了「精简」删内容。若你判断其中有些该升为独立条目，请**报告并等裁定**，不要自行新建。

### P0-2｜索引行的职责是「让我判断要不要读全文」，不是替我读完

**要守的性质**：仅凭索引行（含标题）就足以判断一条是否相关；**行内不承载正文细节**。

- 手段不限：限长、分层、拆多文件、折叠，你选。
- **验收标准（给你定上限，不是指定写法）**：单条索引行 ≤ 150 字符；`INDEX.md` 字符数从 46,514 降到 ≤ 12,000。
- ⚠️ **限长必然丢信息，请守住这条**：被砍掉的内容只能是「完整参数清单 / 逐条踩坑流水 / 量化数据 / 证据链」这类**只有读了全文才需要**的；**不能砍掉「这条管什么、什么条件下适用、什么时候别用」**。砍完后请抽查 10 条最长的，逐条确认判别信息还在。
- ⚠️ 若要拆分多文件，注意 C1：`kb_core.py` 只认 `INDEX.md` 一个文件。拆分方案必须保证主文件仍是完整清单。
- 📌 参考：现有最长索引行 1599 字符（`pitfalls/same-config-key-different-semantics-per-step-type.md`），平均 344 字符——**平均线已经不低，主要矛盾在长尾**。

### P0-3｜写入当下就要拦下坏数据，不能靠事后人工体检

**要守的性质**：**任何一次对 kb 的写入**，若违反 schema、产生死链、或造成索引与磁盘不一致，必须在**写入当下**被拦下并可见。

- 现状证据：用户在本机人工体检查出 **20 处真实问题**且已存在数月无人发现——12 条把 `type` 塞在 `metadata:` 里（memory 格式混入）、3 条 `type` 写成复数、2 条格式完全不合规、3 处 `[[双链]]` 死链。没有任何机制发现它们。
- 手段不限：`PreToolUse` hook、写入脚本内嵌、收尾自检、CI，任选。
- **验收（必须实跑）**：校验器对以下情形全部报错——① 缺 `name/description/type/source/date` 任一 ② `type` 值不在 `tool|workflow|pitfall` 或与所在目录不符 ③ `[[链接]]` 指向不存在的条目 ④ 索引行数 ≠ 磁盘 `.md` 条目数 ⑤ 新增/删除条目后忘记更新索引。
- **可复用**：今天这 20 处的修法已在库里生效，若你要重跑校验器复现「修改前」的行为，先备份再试。
- 📌 本仓库已有 CI（`.cnb.yml`，`python3 -m unittest discover tests/ -v` + 冒烟），若你选择 CI 手段，可以挂在这条流水线上。

## 三、阶段 2（P1｜知识可靠性）

### P1-1｜读者必须能判断一条结论「什么时候、什么版本下实测过」

**要守的性质**：任一条目都能让读者回答：**这条是什么时候验证的？依赖什么版本 / 环境？它现在还成立吗？**

- 现状：**47/110 条正文含版本串**（`v4.27.4`、`rc.26`、`0.16.5`、`3.11.2` 等；宽松口径，正则 `\d+\.\d+|\brc\.?\d+`），却**没有任何字段记录验证时间**。这类结论会随软件升级静默失效，而且失效后看起来仍然像真的。
- 真实代价：一天内就写错两次——① 断言「`VACUUM` 必须退出 ZCode」，被实测证伪（ZCode 运行时可直接跑）② 把单模型观察到的返回结构过度泛化成「所有推理模型都这样」，按用户要求已撤回。
- 手段建议：加 `verified:` 字段（最后实测日期）。**手段不限**，但要能回答上面三个问题。加字段注意 C2（schema 变更要同步注入文本）。
- 含版本串的 47 条请产出**复审清单**（清单形态与优先级由你定，建议按「含版本号 + 该软件是否仍在活跃更新」排序）。
- ⚠️ 复审是**核对**不是**重测**：除非你实际重跑，否则不要改结论。发现无法确认的，标注为待验证而不是删掉。

### P1-2｜作用域标记不能只靠「写一条规矩要求」

**要守的性质**：**单来源实测**的结论，读者**在只读 `description` 的阶段**（不打开全文）就能看出它的适用边界。

- 现状：这条规则已写进 `pitfalls/kb-entry-source-scope-is-the-boundary.md`，但库里照做的极少（用户本机统计 4/110，3.6%）。⇒ 规则存在，执行率近乎为零。
- **反过来的误用也要防**：库里绝大多数条目**本就是通用规律**（bind mount 属主、克隆整行带模板残留、全量 PUT 抹掉脱敏字段…），只是碰巧在某个项目里踩到 ⇒ **不要为了「显得严谨」给通用规律贴作用域标签**。
- 判据（沿用）：**只有当 `description` 里出现具体的数值上限、错误码、返回结构、字段名，却没有点名它属于哪个网关 / 模型 / 平台时**，才需要标作用域。
- 手段不限：可以是机制强制（如「source 含版本号 / 模型名则 description 必须带标记」）、模板要求，或复审清单。**但请勿接受「再写一条元条目要求大家注意」这种手段**——那正是执行率 3.6% 的原因。

## 四、阶段 3（P2｜结构质量）

### P3-1｜要能回答「这个领域的坑都在哪」

**要守的性质**：任选一个领域关键词（如 `tauri` / `windows` / `sqlite` / `mcp` / `git` / `docker`），能一次列出该领域全部相关条目。

- 现状：目录失衡 `pitfalls 72 / workflow 20 / tools 18`；且分类依据是「用户在哪踩到的」而非「这是什么知识」——Tauri、Windows 标题栏、New API 渠道接口、PS 工具 stdout 全在 `pitfalls/`。
- 手段建议：`type` **保持 3 个不动**（它只回答「我该怎么用这条」），另加**正交维度**（如 `topic:` 字段）承载领域归属。**手段不限。**
- ⚠️ **不要靠加 `type` 枚举值解决**。理由有二：一是 `type` 唯一作用是选目录，加值等于加目录，失衡会更重；二是枚举越多越容易赋错——已有活证据：`type` 曾在两个体系间串味（kb 认 `tool|workflow|pitfall`，memory 认 `user|feedback|project|reference`）。
- ⚠️ **`type` 保持 3 个的前提下，注意一个已知空缺**：用户的常驻偏好与纠正（「改文件只动点名范围」「汇报用大白话逐条列」「推荐前先问」等）散落在**项目 memory** 里，按本库收录标准（跨项目可复用）本该进 kb，且现有三类里没有它们的家。**⇒ 项目 memory 不在本仓库内、你也访问不到，所以此项只需要你给出方案与迁移路径，等用户裁定；不要自行新建目录或 `type` 值。**

### P3-2｜读到一条时能找到相关的

**要守的性质**：任一条目都能找到至少一条相关条目。

- 现状：**53/110 条（48%）零入链**，只能靠 INDEX 文本命中找到。kb 现在是扁平列表，不是图。
- 手段不限：补 `[[双链]]`、加「相关条目」小节、建索引关系表。
- 注意：不要为凑指标硬拉关系，**无真实关联就不写**。P3-2 的验收建议放宽为「明显同族（同一失败家族 / 同一工具 / 同一协议）的条目之间无断链」，而不是机械要求 100% 有入链。**若你认为放宽后的标准更合理，请写进回报并说明理由。**
